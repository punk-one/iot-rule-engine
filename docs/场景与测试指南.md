# 电机温度监控场景完整配置指南（v1.5 Wide Mode）

> ⚠️ **重要说明（v1.5 宽表模式）**：
> - 系统现在**仅支持宽表模式**（Wide Mode）
> - Sparkplug Source 输出 Wide Event：一个设备一个事件，所有 metrics 聚合在 `payload.data` 中
> - TimescaleDB Sink 使用新的 Wide Mode 配置格式（不再支持旧的 `target`/`mapping`/`options` 格式）
> - 表结构为宽表格式：每个 metric 对应一列（如 `temp`, `vibration`）
> - 如果在宽表模式下需要聚合特定 metric，需要使用额外的处理节点从 `payload.data` 中提取该字段

## 场景需求

1. 从 Sparkplug B 协议接收电机数据（温度、湿度、震动等）
2. **保存所有原始数据**到原始数据表（`telemetry_raw`）- 宽表格式
3. **可选：对温度数据进行聚合**：计算 1 分钟窗口的平均温度和最大温度（需要额外的处理节点）
4. 当平均温度 > 80°C 且最大温度 > 100°C 时触发告警
5. 将温度聚合数据保存到聚合表（`telemetry_agg`）

**设计要点（宽表模式）**：
- Sparkplug Source 输出 Wide Event：`{payload: {device_id, data: {temp, vibration, ...}}, metadata: {product_type, ...}}`
- 原始数据保存：直接保存 Wide Event 到宽表（所有 metrics 作为列）
- 温度聚合：需要从 `payload.data.temp` 中提取温度值，进行聚合处理
- 使用**并行处理**：原始数据保存和温度聚合可以并行处理

## DAG 设计（宽表模式）

### 方案 1: 仅保存原始数据（推荐 - 最简单）

```
Sparkplug Source (输出 Wide Event)
      ↓
TimescaleDB Sink (保存原始数据到 telemetry_raw 表)
```

**说明**：
- 直接保存 Sparkplug Source 输出的 Wide Event 到宽表
- 所有 metrics 作为列保存（`temp`, `vibration` 等）
- 最简单、最高效的方案
- 聚合可以在 TimescaleDB 中使用 SQL 查询实现

### 方案 2: 保存原始数据 + 温度聚合（需要额外处理节点）

```
Sparkplug Source (输出 Wide Event: {device_id, data: {temp, vibration, ...}})
      ↓
      ├──→ TimescaleDB Sink (保存原始数据到 telemetry_raw 表)
      │
      └──→ Template Transform (从 payload.data.temp 提取温度值)
            ↓
            WindowAggregate (1分钟窗口聚合温度)
            ↓
            Filter (条件过滤: avg_1m > 80 && max_1m > 100)
            ↓
            TimescaleDB Sink (保存聚合数据到 telemetry_agg 表)
```

**说明**（宽表模式下的限制）：
- 分支 1：直接保存 Wide Event 到宽表（所有 metrics 作为列）
- 分支 2：需要从 Wide Event 的 `payload.data.temp` 中提取温度值
  - Template Transform 需要将 Wide Event 转换为适合聚合的格式（提取 `payload.data.temp`）
  - WindowAggregate 聚合温度值
  - 聚合结果需要转换回 Wide Event 格式才能写入宽表
- **注意**：在宽表模式下，聚合特定 metric 需要额外的处理步骤，比窄表模式复杂
- **建议**：如果只需要保存原始数据，使用方案 1；如果需要实时聚合，考虑在 TimescaleDB 中使用连续聚合（Continuous Aggregates）

### 方案 3: 使用 process-normalize-wide（推荐用于生产环境）

```
Sparkplug Source (输出 Wide Event)
      ↓
process-normalize-wide (验证和规范化 Wide Event 格式)
      ↓
      ├──→ TimescaleDB Sink (保存原始数据到 telemetry_raw 表)
      │
      └──→ process-autoschema (自动创建和更新表结构)
            ↓
            TimescaleDB Sink (保存原始数据到 telemetry_raw 表)
```

**说明**：
- `process-normalize-wide`：验证 Wide Event 格式（`payload.device_id`, `payload.data`, `metadata.product_type`）
- `process-autoschema`：自动创建和更新 TimescaleDB 表结构（根据 `payload.data` 中的字段动态添加列）
- 适用于生产环境，确保数据格式正确性和表结构的自动演进

## 数据流说明

### 1. Sparkplug Source 匹配机制

#### 数据流路径

```
MQTT Client (发送 Sparkplug B 消息)
    ↓ Topic: spBv1.0/Factory/DDATA/Line1/Motor1
MQTT Broker
    ↓ Hook.OnPublish() 捕获消息
Ingress (解析 Topic，提取 hint)
    ↓ 发布到 NATS
NATS Topic: ingress.sparkplugb.raw (所有 Sparkplug 数据)
    ↓ Dispatcher 分发
所有 Sparkplug Source 插件 (每个规则中的 Source 节点)
    ↓ 插件内部过滤
匹配的 Sparkplug Source (process.match.group_id == hint.group)
    ↓ 处理并输出
标准 Event 格式
```

#### 匹配规则

**Ingress 处理**：
1. MQTT Broker 接收到 Sparkplug B 消息（Topic: `spBv1.0/{group_id}/{msg_type}/{edge_node}/{device_id}`）
2. Ingress 解析 Topic，提取 hint 信息：
   - `hint.group`: 从 Topic 中提取的 group_id（如 `Factory`）
   - `hint.msg`: 消息类型（如 `DDATA`、`NDATA`）
   - `hint.node`: Edge Node（如 `Line1`）
   - `hint.device`: Device ID（如 `Motor1`）
3. Ingress 发布到 NATS Topic: `ingress.sparkplugb.raw`（**所有 Sparkplug 数据都发布到这里**）
4. Event Metadata 中包含所有 hint 信息

**Sparkplug Source 匹配**：
1. Dispatcher 将 `ingress.sparkplugb.raw` 的事件分发给**所有** Source Plugin
2. 每个 Sparkplug Source 插件的 `OnEvent()` 方法接收所有事件
3. 插件内部进行过滤：
   - **必需匹配**：`process.match.group_id` == `hint.group`
   - **可选匹配**：`process.match.msg_types` 包含 `hint.msg`（如果配置了）
4. 只有匹配的事件才会被处理并转换为标准 Event 格式

#### 输出格式

**输入**（来自 Ingress）：
- NATS Topic: `ingress.sparkplugb.raw`
- Event Metadata: `{ "protocol": "sparkplugb", "hint.group": "Factory", "hint.msg": "DDATA", ... }`
- Event Payload: `{ "topic": "spBv1.0/Factory/DDATA/Line1/Motor1", "raw": "<base64编码的protobuf>" }`

**输出**（匹配后处理，Wide Mode）：
- Sparkplug Source **将所有 metrics 聚合为一个设备事件**（宽表模式）
- 如果一条 Sparkplug B 消息包含多个 metric（如 `temp` 和 `vibration`），会生成一个 Wide Event：

**Wide Event**（包含所有 metrics）：
```json
{
  "payload": {
    "device_id": "Motor1",
    "data": {
      "temp": 85.5,
      "vibration": 5.2
    }
  },
  "metadata": {
    "protocol": "sparkplugb",
    "product_type": "motor",
    "device_id": "Motor1",
    "mqtt_topic": "spBv1.0/Factory/DDATA/Line1/Motor1"
  },
  "timestamp": "2024-01-01T12:00:00Z"
}
```

**说明**：
- 一个设备一个事件，所有 metrics 聚合在 `payload.data` 中
- 每个 metric 作为 `payload.data` 的一个键（如 `temp`, `vibration`）
- 符合宽表设计：一次事件 = 一行时序数据
- `metadata.product_type` 用于路由到对应的 TimescaleDB 宽表

#### 多数据源、多规则场景

**场景示例**：
- 数据源 1：`group_id = "Factory"`，设备：Motor1, Motor2
- 数据源 2：`group_id = "Warehouse"`，设备：Sensor1, Sensor2
- 规则 1：监控 Factory 的温度数据
- 规则 2：监控 Warehouse 的湿度数据

**配置方式**：

**规则 1 - Sparkplug Source 配置**：
```json
{
  "process": {
    "match": {
      "group_id": "Factory",
      "msg_types": ["DDATA"]
    }
  }
}
```
- 只接收 `group_id = "Factory"` 的 `DDATA` 消息
- 忽略 `Warehouse` 的数据

**规则 2 - Sparkplug Source 配置**：
```json
{
  "process": {
    "match": {
      "group_id": "Warehouse",
      "msg_types": ["DDATA"]
    }
  }
}
```
- 只接收 `group_id = "Warehouse"` 的 `DDATA` 消息
- 忽略 `Factory` 的数据

**工作原理**：
1. 所有 Sparkplug 数据都发布到同一个 NATS Topic: `ingress.sparkplugb.raw`
2. Dispatcher 将事件分发给所有规则的 Source 节点
3. 每个 Source 节点通过 `process.match.group_id` 进行过滤
4. 只有匹配的事件才会进入该规则的 DAG 处理流程
5. 不同规则可以配置不同的 `group_id` 来接收不同的数据源

**注意事项**：
- 所有 Source 节点都会收到所有事件，但只有匹配的才会处理
- 如果多个规则配置相同的 `group_id`，它们都会处理相同的数据源（数据会被复制到多个规则）
- 可以通过 `process.match.msg_types` 进一步细化过滤（如只接收 `DDATA`，忽略 `NDATA`）
- 匹配是在插件内部进行的，不匹配的事件会被静默忽略（返回 `nil`，不报错）

#### 关键点总结

1. **Ingress 统一入口**：
   - 所有 Sparkplug B 数据都发布到 `ingress.sparkplugb.raw`
   - Ingress 从 Topic 中提取 hint 信息（group_id, msg_type 等）

2. **Dispatcher 广播分发**：
   - Dispatcher 将 `ingress.sparkplugb.raw` 的事件分发给**所有**规则的 Source Plugin
   - 每个 Source Plugin 都会收到所有事件

3. **插件内部过滤**：
   - 每个 Sparkplug Source 插件通过 `process.match.group_id` 匹配 `hint.group`
   - 可选通过 `process.match.msg_types` 匹配 `hint.msg`
   - 只有匹配的事件才会被处理

4. **多规则支持**：
   - 不同规则可以配置不同的 `group_id` 来接收不同的数据源
   - 多个规则可以配置相同的 `group_id` 来同时处理相同的数据源
   - 每个规则独立处理，互不干扰

### 2. Wide Event 处理（宽表模式）

在宽表模式下，Sparkplug Source 直接输出 Wide Event，无需额外的 Transform：

**Wide Event 格式**（来自 Sparkplug Source）：
```json
{
  "payload": {
    "device_id": "Motor1",
    "data": {
      "temp": 85.5,
      "vibration": 5.2
    }
  },
  "metadata": {
    "protocol": "sparkplugb",
    "product_type": "motor",
    "device_id": "Motor1"
  },
  "timestamp": "2024-01-01T12:00:00Z"
}
```

**说明**：
- Sparkplug Source 已经输出标准 Wide Event 格式
- 如果仅需要保存原始数据，可以直接使用 TimescaleDB Sink
- 如果需要聚合特定 metric，需要使用 Template Transform 从 `payload.data` 中提取该字段

### 3. WindowAggregate 聚合（并行节点）

WindowAggregate 按 `device_id` 和 `metric` 分组，在 1 分钟窗口内计算平均值和最大值：

**并行处理能力**：
- WindowAggregate 是一个**并行节点**，可以与其他处理流程并行运行
- 在并行处理场景中，WindowAggregate 只处理特定 metric（如温度）的聚合
- 其他 metric（如湿度、震动）可以并行保存到原始数据表

**多 Metric 处理机制**：
- 由于 Sparkplug Source 为每个 metric 生成独立事件，WindowAggregate 会为每个 `(device_id, metric)` 组合维护独立的状态
- 例如：`(Motor1, temp)` 和 `(Motor1, vibration)` 是两个独立的状态窗口
- 每个 metric 的聚合结果会独立输出

**并行处理场景**：
- **场景**：上报数据包含多个变量（温度、湿度、震动等）
- **需求**：只聚合温度数据到温度聚合表，同时保存所有原始数据到原始数据表
- **实现**：使用并行分支
  - 分支 1：Filter（`payload.metric == "temp"`）→ WindowAggregate → Filter → 温度聚合表
  - 分支 2：直接保存所有原始数据到原始数据表

**输入示例**（来自 Template Transform）：
- 事件 1：`{ "device_id": "Motor1", "metric": "temp", "value": 85.5, "ts": "..." }`
- 事件 2：`{ "device_id": "Motor1", "metric": "temp", "value": 90.2, "ts": "..." }`
- 事件 3：`{ "device_id": "Motor1", "metric": "vibration", "value": 5.2, "ts": "..." }`
- 事件 4：`{ "device_id": "Motor1", "metric": "vibration", "value": 5.5, "ts": "..." }`

**输出**（1 分钟窗口关闭时，每个 metric 独立输出）：

**输出 1**（温度聚合）：
```json
{
  "device_id": "Motor1",
  "metric": "temp",
  "avg_1m": 87.5,
  "max_1m": 105.2,
  "ts": "2024-01-01T12:01:00Z"
}
```

**输出 2**（振动聚合）：
```json
{
  "device_id": "Motor1",
  "metric": "vibration",
  "avg_1m": 5.35,
  "max_1m": 5.5,
  "ts": "2024-01-01T12:01:00Z"
}
```

**说明**：
- `state.key_by: ["device_id", "metric"]` 确保每个 metric 有独立的状态窗口
- 如果只关心温度数据，可以在 Filter 中过滤 `metric == "temp"`
- 如果需要同时监控多个 metric，每个 metric 会独立聚合和输出

### 4. Filter 过滤

Filter 使用 CEL 表达式过滤，只有满足条件的事件才会进入下游：

**条件**：`payload.avg_1m > 80 && payload.max_1m > 100`

**多 Metric 场景**：
- 由于 WindowAggregate 为每个 metric 独立输出，Filter 会分别处理每个 metric 的聚合结果
- 如果只想监控温度数据，可以添加 metric 过滤：`payload.metric == "temp" && payload.avg_1m > 80 && payload.max_1m > 100`
- 如果同时监控多个 metric，每个 metric 的聚合结果会独立通过 Filter 检查

### 5. TimescaleDB Sink 保存

TimescaleDB Sink 将聚合数据写入数据库表。

## 完整节点配置（v1.5 格式）

### 1. Sparkplug Source

**节点类型**: `source-sparkplug-ingress`

**配置**:
```json
{
  "process": {
    "match": {
      "group_id": "Factory",
      "msg_types": ["DDATA"]
    },
    "extract": {
      "product_type": "hint.group"
    }
  }
}
```

**说明**:
- 从 Ingress 接收 Sparkplug B 数据
- `process.match.group_id`: Sparkplug Group ID（必需），用于过滤 `hint.group`
- `process.match.msg_types`: 消息类型过滤（可选），如 `["NDATA", "DDATA"]`，不设置则接收所有类型
- `process.extract.product_type`: 提取 product_type 的路径（可选），如 `"hint.group"` 或固定值，用于路由到对应的 TimescaleDB 宽表
- 输出 Wide Event 格式：`{payload: {device_id, data: {temp, vibration, ...}}, metadata: {product_type, ...}}`
- **注意**：系统现在强制使用 Wide Mode，不再支持 Narrow Mode（每个 metric 一个事件）

### 2. Template Transform（仅在需要提取特定 metric 时使用）

**节点类型**: `transform-template-expand`

**使用场景**：仅在需要从 Wide Event 中提取特定 metric 进行聚合时使用

**配置示例**（提取温度值用于聚合）:
```json
{
  "process": {
    "template": "{\"device_id\": \"{{payload.device_id}}\", \"value\": {{payload.data.temp}}, \"ts\": \"{{timestamp}}\"}",
    "iterate": ""
  },
  "output": {
    "mode": "replace"
  }
}
```

**说明**:
- `process.template`: JSON 字符串格式（format: "json"），使用 `{{variable}}` 模板语法
- `{{payload.device_id}}`: 从 Wide Event 获取设备ID
- `{{payload.data.temp}}`: 从 Wide Event 的 `payload.data` 中提取温度值
- `{{timestamp}}`: 使用事件时间戳
- **注意**：在宽表模式下，如果仅需要保存原始数据，不需要使用 Template Transform
- **注意**：如果需要聚合，Template Transform 将 Wide Event 转换为适合聚合的格式

---

### 3. WindowAggregate

**节点类型**: `aggregate-window`

**配置**:
```json
{
  "state": {
    "key_by": ["device_id", "metric"]
  },
  "process": {
    "window": {
      "type": "tumbling",
      "size": "1m"
    },
    "aggregations": [
      {
        "field": "value",
        "func": "avg",
        "alias": "avg_1m"
      },
      {
        "field": "value",
        "func": "max",
        "alias": "max_1m"
      }
    ]
  },
  "output": {
    "emit": "on_window_close"
  }
}
```

**说明**:
- **并行处理能力**：WindowAggregate 是并行节点，可以与其他处理流程并行运行
  - 在并行处理场景中，WindowAggregate 只处理特定 metric（如温度）的聚合
  - 其他 metric（如湿度、震动）可以并行保存到原始数据表
- `state.key_by`: 按 `device_id` 和 `metric` 分组状态
  - **重要**：每个 `(device_id, metric)` 组合有独立的状态窗口
  - 例如：`(Motor1, temp)` 和 `(Motor1, vibration)` 是两个独立的状态
  - 如果一条 Sparkplug B 消息包含多个 metric，每个 metric 会独立聚合
- `process.window.type`: `tumbling` 表示固定窗口
- `process.window.size`: `1m` 表示 1 分钟窗口
- `process.aggregations`: 定义聚合函数
  - `avg`: 计算平均值，别名为 `avg_1m`
  - `max`: 计算最大值，别名为 `max_1m`
  - **注意**：聚合函数作用于 `field: "value"`，即每个 metric 的 value 字段
- `output.emit`: `on_window_close` 表示窗口关闭时输出
  - 每个 metric 的窗口独立计时，独立输出
- **并行处理场景**：
  - 场景：上报数据包含多个变量（温度、湿度、震动等）
  - 需求：只聚合温度数据到温度聚合表，同时保存所有原始数据到原始数据表
  - 实现：使用并行分支
    - 分支 1：Filter（`payload.metric == "temp"`）→ WindowAggregate → Filter → 温度聚合表
    - 分支 2：直接保存所有原始数据到原始数据表

---

### 4. Filter

**节点类型**: `filter-by-expression`

**配置**:
```json
{
  "process": {
    "condition": {
      "expr": "payload.avg_1m > 80 && payload.max_1m > 100"
    }
  },
  "output": {
    "mode": "replace"
  }
}
```

**说明**:
- `process.condition.expr`: CEL 表达式（必需），用于过滤事件
- 只有满足条件的事件（平均温度 > 80°C 且最大温度 > 100°C）才会进入下游
- 不满足条件的事件会被丢弃
- **多 Metric 处理**：如果 Sparkplug B 消息包含多个 metric（如 temp 和 vibration），每个 metric 的聚合结果会独立通过 Filter 检查
- **可选**：如果只想监控特定 metric，可以在表达式中添加 `payload.metric == "temp"` 条件
- `output.mode`: 输出模式（可选），`replace`（默认）、`merge`、`enrich`

---

### 6. TimescaleDB Sink（原始数据表 - Wide Mode）

**节点类型**: `sink-timeseries-timescaledb`

**配置**:
```json
{
  "dsn": "postgres://user:pass@localhost:5432/db",
  "table": "telemetry_raw",
  "time_column": "time",
  "device_id_column": "device_id",
  "payload_column": "payload.data",
  "extra": {
    "unknown_to_jsonb": true,
    "jsonb_column": "ext"
  }
}
```

**说明**:
- `dsn`: PostgreSQL 连接字符串（必需）
- `table`: 目标表名（`telemetry_raw` - 原始数据表，支持 `${metadata.product_type}` 变量替换）
- `time_column`: 时间列名（默认: `time`）
- `device_id_column`: 设备ID列名（默认: `device_id`）
- `payload_column`: payload数据路径（默认: `payload.data`），Wide Mode下从 `payload.data` 中提取所有字段作为列
- `extra.unknown_to_jsonb`: 是否将未知字段写入JSONB列（可选）
- `extra.jsonb_column`: JSONB列名（默认: `ext`）
- **用途**：保存所有 metrics 的原始数据到宽表，每个 metric 对应一列（如 `temp`, `vibration`）
- **数据来源**：直接来自 Sparkplug Source 的 Wide Event 输出
- **注意**：系统现在仅支持 Wide Mode，不再使用旧的 `target`/`mapping`/`options` 配置格式

**说明**:

- `time_column`: 时间列名（默认: `time`）
- `device_id_column`: 设备ID列名（默认: `device_id`）

- `extra.jsonb_column`: JSONB列名（默认: `ext`）
- **用途**：保存温度聚合数据（`avg_1m`, `max_1m` 等聚合结果）
- **数据来源**：来自聚合流程（WindowAggregate → Filter）的输出

## TimescaleDB 表结构（Wide Mode）

### 1. 原始数据表（telemetry_raw）

```sql
-- 创建原始数据表（宽表格式：每个 metric 一列）
CREATE TABLE telemetry_raw (
  time timestamptz NOT NULL,
  device_id text NOT NULL,
  temp double precision,          -- 温度 metric
  vibration double precision,     -- 振动 metric
  ext jsonb                       -- 其他未知字段（JSONB）
);

-- 创建超表（TimescaleDB 特性）
SELECT create_hypertable('telemetry_raw', 'time', partitioning_column => 'device_id');

-- 创建索引（提高查询性能）
CREATE INDEX idx_telemetry_raw_device ON telemetry_raw(device_id);
CREATE INDEX idx_telemetry_raw_time ON telemetry_raw(time DESC);
```

**说明**：
- 宽表格式：每个 metric 对应一列（`temp`, `vibration` 等）
- 保存所有 metrics 的原始数据，不进行聚合
- 一次事件 = 一行数据，包含该时间点的所有 metrics
- `ext` JSONB 列用于存储未知字段（如果配置了 `extra.unknown_to_jsonb: true`）
- 用于数据回溯和完整历史记录

### 2. 聚合数据表（telemetry_agg）

```sql
-- 创建聚合数据表（保存温度聚合结果）
CREATE TABLE telemetry_agg (
  time timestamptz NOT NULL,
  device_id text NOT NULL,
  avg_1m double precision,        -- 1分钟平均温度
  max_1m double precision,        -- 1分钟最大温度
  ext jsonb                       -- 其他未知字段（JSONB）
);

-- 创建超表（TimescaleDB 特性）
SELECT create_hypertable('telemetry_agg', 'time', partitioning_column => 'device_id');

-- 创建索引（提高查询性能）
CREATE INDEX idx_telemetry_agg_device ON telemetry_agg(device_id);
CREATE INDEX idx_telemetry_agg_time ON telemetry_agg(time DESC);
```

**说明**：
- 宽表格式：聚合结果字段作为列（`avg_1m`, `max_1m` 等）
- 只保存温度聚合数据（经过 Filter 过滤后的结果）
- 只包含满足告警条件的数据（avg_1m > 80 && max_1m > 100）
- 用于告警查询和趋势分析
- **注意**：在宽表模式下，如果需要聚合特定 metric，需要在处理链中从 `payload.data` 中提取该字段

   - 从节点面板拖拽 `filter-by-expression`

6. **TimescaleDB Sink（聚合数据）** - 分支 2
   - 从节点面板拖拽 `sink-timeseries-timescaledb`
   - 配置 `target.dsn`（PostgreSQL 连接字符串）
   - 配置 `target.table`（`telemetry_agg`）
   - 配置 `mapping`（列映射：`device_id`, `metric`, `avg_1m`, `max_1m`, `time`）
   - 配置 `options.time_column`（`time`）

### 步骤 3: 连接节点

按照 DAG 设计（方案 2：并行处理）连接节点：

**主流程**：
- Sparkplug Source → Template Transform

**分支 1（原始数据保存）**：
- Template Transform → TimescaleDB Sink（原始数据）

**分支 2（温度聚合告警）**：
- Template Transform → Filter（温度过滤）
- Filter（温度过滤） → WindowAggregate（温度聚合）

- Filter（告警条件） → TimescaleDB Sink（聚合数据）

**说明**：
- Template Transform 的输出同时连接到两个分支（并行处理）
- 分支 1 直接保存所有原始数据
- 分支 2 只处理温度数据，进行聚合和告警

## 故障排查

### 问题 1: 没有数据写入 TimescaleDB

**可能原因**：
1. Filter 条件太严格，所有数据都被过滤
2. WindowAggregate 窗口未触发
3. TimescaleDB 连接失败

**排查步骤**：
1. 检查 Sparkplug Source 的 `process.match.group_id` 是否与测试数据的 group_id 匹配
2. 检查 Filter 的 CEL 表达式（`process.condition.expr`）是否正确
3. 检查 WindowAggregate 的窗口配置（`process.window.size: "1m"`）
4. 检查 TimescaleDB Sink 的连接字符串（`target.dsn`）
5. 查看规则引擎日志

### 问题 2: 聚合值不正确

**可能原因**：
1. `state.key_by` 配置错误，导致分组不正确
2. 聚合字段路径错误

**排查步骤**：
1. 检查 `state.key_by` 是否包含 `["device_id", "metric"]`
2. 检查 `process.aggregations[].field` 是否为 `"value"`
3. 查看 WindowAggregate 的输入数据格式

### 问题 3: 时间戳格式错误

**可能原因**：
1. Template Transform 的 `{{timestamp}}` 格式不正确
2. TimescaleDB 时间列类型不匹配

**排查步骤**：
1. 检查 Template Transform 输出的 `ts` 字段格式
2. 检查 TimescaleDB 表的 `time` 列类型（应为 `timestamptz`）
3. 检查 `mapping.time` 路径是否正确

## 总结（v1.5 宽表模式）

**主要配置要点**：
1. **Sparkplug Source**:
   - 使用 `process.match.group_id` 匹配 Ingress 的 group_id
   - 可选配置 `process.match.msg_types` 过滤消息类型
   - 可选配置 `process.extract.product_type` 提取 product_type（用于路由）
   - **输出 Wide Event**：一个设备一个事件，所有 metrics 在 `payload.data` 中

2. **TimescaleDB Sink（Wide Mode）**:
   - 使用 `dsn` 和 `table` 配置连接（不再使用 `target`/`mapping`/`options`）
   - `payload_column` 指定数据路径（默认: `payload.data`）
   - `time_column` 和 `device_id_column` 配置时间列和设备ID列
   - `extra.unknown_to_jsonb` 配置未知字段处理
   - **自动展开**：`payload.data` 中的字段自动映射为数据库列

3. **表结构（宽表格式）**：
   - 每个 metric 对应一列（如 `temp`, `vibration`）
   - 一次事件 = 一行数据，包含该时间点的所有 metrics
   - 支持动态添加列（通过 `process-autoschema` 插件）

**数据流（宽表模式）**：
- Sparkplug Source → 输出 Wide Event（一个设备一个事件，所有 metrics 在 `payload.data` 中）
- TimescaleDB Sink → 直接保存 Wide Event 到宽表（所有 metrics 作为列）

**宽表模式 vs 窄表模式的变化**：
1. **Sparkplug Source**：
   - ❌ 旧：一条消息包含 N 个 metric → 生成 N 个独立事件
   - ✅ 新：一条消息包含 N 个 metric → 生成 1 个 Wide Event（所有 metrics 在 `payload.data` 中）

2. **TimescaleDB Sink**：
   - ❌ 旧：使用 `target`/`mapping`/`options` 配置，需要手动映射每个字段
   - ✅ 新：使用 `dsn`/`table`/`payload_column` 配置，自动展开 `payload.data` 中的字段为列

3. **表结构**：
   - ❌ 旧：窄表格式（`time, device_id, metric, value`）
   - ✅ 新：宽表格式（`time, device_id, temp, vibration, ...`，每个 metric 一列）

4. **聚合处理**：
   - ❌ 旧：可以直接对单个 metric 事件进行聚合
   - ✅ 新：需要从 Wide Event 的 `payload.data` 中提取特定 metric，然后聚合（更复杂）

**建议**：
- **仅保存原始数据**：使用最简单的流程（Sparkplug Source → TimescaleDB Sink）
- **需要聚合**：考虑在 TimescaleDB 中使用连续聚合（Continuous Aggregates）而不是在数据流中聚合
- **生产环境**：使用 `process-normalize-wide` 和 `process-autoschema` 确保数据格式和表结构正确

# Part 2️⃣

# ChangeDetect / WindowAgg 的「性能级实现设计」

> 目标：
> **在规则引擎中长期运行、百万级 telemetry、可预测内存、可调优**

---

## 一、Stateful Plugin 的统一运行模型（性能前提）

### 1️⃣ 状态 = Keyed State（必须）

所有 Stateful Plugin **必须**基于 Key 进行状态隔离：

```text
state_key = hash(group_by fields)
```

例如：

```json
group_by: ["device_id", "metric"]
```

生成：

```text
state_key = plc-01|temperature
```

> ❗这是保证：
>
> * 横向扩展
> * 内存可控
> * 逻辑正确
>   的根本前提

---

## 二、ChangeDetect Plugin（升级版）

### 2.1 功能边界（严格）

| 能力       | 是否支持                    |
| -------- | ----------------------- |
| 与上一次比较   | ✅                       |
| 与 N 次前比较 | ❌（不需要）                  |
| 百分比变化    | ✅                       |
| 趋势判断     | ✅                       |
| 条件输出     | ✅                       |
| 多字段      | ❌（交给 Template / Window） |

---

### 2.2 内部状态结构（极简 & 高效）

```go
type ChangeState struct {
    LastValue float64
    LastTs    time.Time
}
```

📌 **只存 1 条历史**
这是 ChangeDetect 高性能的关键。

---

### 2.3 配置 Schema（核心）

```json
{
  "group_by": ["device_id", "metric"],
  "field": "value",
  "mode": "delta | percent | trend",
  "threshold": 5,
  "direction": "increase | decrease | any",
  "emit_policy": "on_change | always"
}
```

---

### 2.4 执行逻辑（伪代码）

```go
state := getState(key)

if state exists {
    delta := curr - state.LastValue
    matched := eval(delta, cfg)

    if matched {
        emit(event with delta)
    }
}

update state
```

---

### 2.5 性能特性总结

| 指标  | 表现           |
| --- | ------------ |
| 内存  | O(N keys)    |
| CPU | O(1) / event |
| GC  | 极低           |
| 延迟  | < 微秒级        |

👉 **适合：**

* 告警触发
* 边缘侧运行
* 高频数据

## 三、WindowAgg Plugin（工业级设计）

### 3.1 为什么 Window 是最难的？

因为它涉及：

* 时间
* 状态
* 内存
* 乱序
* 迟到数据

所以 **一定要严格约束功能边界**

---

### 3.2 Window 类型（v1.1 必须支持）

| 类型       | 说明   |
| -------- | ---- |
| Tumbling | 固定窗口 |
| Sliding  | 滑动窗口 |
| Count    | 按条数  |

---

### 3.3 状态结构设计（关键）

#### Tumbling / Sliding

```go
type WindowState struct {
    Buckets map[int64]*AggBucket
}
```

```go
type AggBucket struct {
    Count int64
    Sum   float64
    Max   float64
    Min   float64
}
```

📌 **Bucket = 时间片**
例如 1s / 5s 对齐

---

### 3.4 窗口配置 Schema（完整版）

```json
{
  "group_by": ["device_id", "metric"],
  "window": {
    "type": "sliding",
    "size": "1m",
    "slide": "10s"
  },
  "aggregations": [
    { "field": "value", "func": "avg", "alias": "avg_1m" },
    { "field": "value", "func": "max", "alias": "max_1m" }
  ],
  "emit_policy": "on_window_close | periodic",
  "lateness": "5s"
}
```

---

### 3.5 执行策略（重点）

#### 推荐：**时间轮 + Lazy Evict**

* 不用定时器 per key
* 只在新事件到来时：

  * 计算当前 bucket
  * 清理过期 bucket

```go
now := align(ts)
bucket := now / bucketSize
```

---

### 3.6 输出事件结构（统一）

```json
{
  "payload": {
    "device_id": "plc-01",
    "metric": "temperature",
    "avg_1m": 36.5,
    "max_1m": 42.0,
    "window_start": "...",
    "window_end": "..."
  }
}
```

---

### 3.7 性能与资源上限（可控）

| 项  | 控制方式               |
| -- | ------------------ |
| 内存 | max_keys × buckets |
| 延迟 | 无锁 / 单 goroutine   |
| GC | 定长 bucket          |
| 异常 | 自动丢弃迟到数据           |

# Part 3️⃣

## 场景：电机温度监控

**需求：**

1. 实时保存原始数据

```
      └──→ Alert + Command
```
