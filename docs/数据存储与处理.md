# IoT Rule Engine 系统数据库设计

本文档描述以 **PostgreSQL** 作为数据库后端时，规则引擎涉及的数据库表结构、配置及插件依赖关系。

**命名规范**：
- 所有规则引擎相关表以 `re_` 开头（如 `re_rules`、`re_config`）
- 系统用户表为 `sys_users`（不以 `re_` 开头）

---

## 1. 概述

### 1.1 PostgreSQL 使用场景

| 场景 | 说明 | 配置位置 |
|------|------|----------|
| **规则存储** | Manager 将规则、快照、灰度配置等持久化到 PostgreSQL | `manager.storage_type: postgres`，`configs/config-default.yaml` 的 `database` |
| **设备影子** | sink-shadow-store 插件将设备影子写入 PG | 插件配置 `target.dsn`、`target.table` |
| **时序数据** | sink-timeseries-timescaledb 写入时序表 | 插件配置 `output.dsn`、`output.table` |
| **关系型写入** | sink-relational-postgres 写入用户自定义表 | 插件配置 `output.target.dsn`、`output.target.table` |
| **自动建表** | process-autoschema 按数据推断 schema 并建表 | 插件配置 `dsn`、`table`、`schema_registry` |

### 1.2 初始化脚本

所有 **系统表** 及 **常用插件表** 的 DDL 已整理在：

```
docs/init.sql
```

在目标 PostgreSQL 库中执行该脚本即可完成表结构初始化。业务表（如时序 telemetry）可根据需要自行创建或由 AutoSchema 动态创建。

## 2. 配置说明

### 2.1 规则存储（Manager）

当 `manager.storage_type: postgres` 时，规则引擎使用 PostgreSQL 存储规则与配置。数据库连接来自全局 `database` 配置：

```yaml
# configs/config-default.yaml

database:
  host: "localhost"
  port: 5432
  name: "your_db"
  user: "your_user"
  password: "your_password"
  ssl_mode: "disable"
  max_idle_conns: 10
  max_open_conns: 100
  conn_max_lifetime_minutes: 60

manager:
  storage_type: "postgres"   # sqlite | boltdb | postgres
  db_path: "./data"          # storage_type 为 sqlite/boltdb 时使用
```

**说明**：`postgres` 存储类型已在代码中实现（见 `internal/infra/storage/rulesdb/postgres_db.go`），使用 **GORM** 作为 ORM 框架。

**实现特点**：
- 使用 `gorm.io/gorm` 和 `gorm.io/driver/postgres v1.6.0`
- 表结构通过 GORM `AutoMigrate` 自动创建（首次连接时）
- 所有表使用 `re_` 前缀（通过 GORM 模型的 `TableName()` 方法指定）
- 支持连接池配置（MaxIdleConns, MaxOpenConns, ConnMaxLifetime）
- 使用 GORM 的 `clause.OnConflict` 实现 UPSERT 操作
- 实现完整的 `RulesDB` 接口，与 SQLite 实现功能对等

### 2.2 插件与数据库

各插件**独立配置** DSN 与表名，可与规则存储使用同一 PG 实例，也可使用不同库/实例：

- **sink-shadow-store**：`target.dsn`、`target.table`（默认 `re_device_shadow`）
- **sink-timeseries-timescaledb**：`output.dsn`、`output.table`
- **sink-relational-postgres**：`output.target.dsn`、`output.target.table`
- **process-autoschema**：`dsn`、`table`，可选 `schema_registry.table`（默认 `re_schema_registry`）

## 5. 使用流程建议

1. **创建数据库**：在 PostgreSQL 中创建库（如 `pulse_iot`）。
2. **配置规则存储**：在 `configs/config-default.yaml` 中设置：
   ```yaml
   manager:
     storage_type: "postgres"

   database:
     host: "localhost"
     port: 5432
     name: "your_db"
     user: "your_user"
     password: "your_password"
     ssl_mode: "disable"
     max_idle_conns: 10
     max_open_conns: 100
     conn_max_lifetime_minutes: 60
   ```
3. **自动创建表**：首次启动时，GORM 会自动创建规则引擎系统表（`re_rules`, `re_config`, `re_snapshots`, `re_gray_release`）。
4. **手动初始化（可选）**：如需手动创建表或创建系统用户表、插件表，可执行 `docs/init.sql`。
5. **配置插件**：为 shadow-store、timescaledb、postgres、autoschema 等配置对应 DSN 与表名。
6. **业务表**：时序表等可按示例自建，或交给 AutoSchema 管理；若用 TimescaleDB，需先 `CREATE EXTENSION timescaledb`。

## 6. 技术实现细节

### 6.1 GORM 模型定义

PostgreSQL 存储实现使用 GORM 模型定义表结构，位于 `internal/infra/storage/rulesdb/postgres_db.go`：

- **ReRule**：规则表模型，对应 `re_rules`
- **ReConfig**：配置表模型，对应 `re_config`
- **ReSnapshot**：快照表模型，对应 `re_snapshots`
- **ReGrayRelease**：灰度发布配置表模型，对应 `re_gray_release`

所有模型通过 `TableName()` 方法指定表名（`re_` 前缀）。

### 6.2 自动迁移

首次连接 PostgreSQL 时，GORM 会执行 `AutoMigrate` 自动创建表结构：

```go
db.AutoMigrate(&ReRule{}, &ReConfig{}, &ReSnapshot{}, &ReGrayRelease{})
```

### 6.3 连接管理

- 使用 GORM PostgreSQL 驱动（键值对格式 DSN）
- 支持连接池配置（通过 `sql.DB` 设置）
- 使用反射提取配置字段，避免循环导入

### 6.4 接口实现

`PostgresDB` 实现了完整的 `RulesDB` 接口（19 个方法）：
- 规则操作：SaveRule, GetRule, ListRules, DeleteRule, RuleExists
- 配置操作：SaveConfig, GetConfig, ConfigExists
- Watch 操作：WatchRules（轮询机制，1秒间隔）
- 快照操作：SaveSnapshot, GetSnapshot, ListSnapshots, GetLatestSnapshot
- 灰度发布：SaveGrayReleaseConfig, GetGrayReleaseConfig, DeleteGrayReleaseConfig

# 二、rulesdb：唯一 DB Owner 实现（关键代码）

## 1️⃣ `internal/infra/storage/rulesdb/db.go`

```go
package rulesdb

import (
	"fmt"
	"path/filepath"
	"time"

	bolt "go.etcd.io/bbolt"
)

type DB struct {
	db *bolt.DB
}

type Config struct {
	DataDir string
	Timeout time.Duration
}

func Open(cfg Config) (*DB, error) {
	if cfg.Timeout == 0 {
		cfg.Timeout = 5 * time.Second
	}

	path := filepath.Join(cfg.DataDir, "rules.db")

	bdb, err := bolt.Open(path, 0644, &bolt.Options{
		Timeout: cfg.Timeout,
	})
	if err != nil {
		return nil, fmt.Errorf("open rules.db failed: %w", err)
	}

	return &DB{db: bdb}, nil
}

func (d *DB) Bolt() *bolt.DB {
	return d.db
}

func (d *DB) Close() error {
	if d.db == nil {
		return nil
	}
	return d.db.Close()
}
```

⚠️ **注意这里没有：**

* ❌ global singleton
* ❌ refCount
* ❌ 多次 Open 保护

👉 **因为这些应该由 Engine 层保证**

# 三、Engine：v1.3.1 正式修复的“根因代码”

## 3️⃣ `internal/core/engine/engine.go`

**这是解决你当前报错的关键代码**

```go
package engine

import (
	"context"

	"your_project/internal/infra/storage/rulesdb"
)

type Engine struct {
	db *rulesdb.DB

	manager  *Manager
	executor *Executor
	pipeline *Pipeline
}

func NewEngine(cfg Config) (*Engine, error) {
	db, err := rulesdb.Open(rulesdb.Config{
		DataDir: cfg.DataDir,
	})
	if err != nil {
		return nil, err
	}

	mgr := NewManager(db)
	exe := NewExecutor(db)
	pipe := NewPipeline(db)

	return &Engine{
		db:       db,
		manager:  mgr,
		executor: exe,
		pipeline: pipe,
	}, nil
}

func (e *Engine) Run(ctx context.Context) error {
	// 顺序启动，避免任何并发初始化
	if err := e.manager.Start(ctx); err != nil {
		return err
	}
	if err := e.executor.Start(ctx); err != nil {
		return err
	}
	if err := e.pipeline.Start(ctx); err != nil {
		return err
	}
	return nil
}

func (e *Engine) Close() error {
	return e.db.Close()
}
```

### 这一段解决了什么？

✅ **rules.db 只会 Open 一次**
✅ **不会并发 Open**
✅ **BoltDB timeout 不再是核心问题**

# 《TimescaleDB Sink v1.5（Wide Mode）完整设计规范》

> 适用版本：**规则引擎 v1.5 RC+**
> 状态：**建议冻结（Freeze Candidate）**

## 1. 设计目标（Design Goals）

### 1.1 业务目标

* 支持 **设备整包状态上报**
* 同一 **产品类型（product_type） → 同一 TimescaleDB 宽表**
* 一次事件 = **一行时序数据**
* 不拆 metric，不走 metric/value 窄表
* 面向：

  * 设备状态趋势
  * 多指标联合分析
  * 实时监控 / 工业报表

---

### 1.2 架构目标

* Ingress **只做协议转换**
* Source **只做协议到业务模型的映射**
* Process **只做结构整形 / 补充**
* Sink **只做确定性写入**
* TimescaleDB Wide Mode 成为 **一等公民**

---

## 2. Wide Mode 数据模型定义（核心）

### 2.1 事件语义（Wide Event）

```json
{
  "id": "uuid",
  "timestamp": "2025-01-01T12:00:00Z",
  "payload": {
    "device_id": "dbm102",
    "data": {
      "alarm": false,
      "result_below_ang": 0,
      "result_static": 15,
      "s20": 1103,
      "wheel_id": 45
    }
  },
  "metadata": {
    "protocol": "mqtt",
    "product_type": "dbm",
    "device_id": "dbm102"
  }
}
```

### 2.2 语义约束（强约束）

| 字段                      | 约束               |
| ----------------------- | ---------------- |
| `payload.device_id`     | 必须存在             |
| `payload.data`          | object，key = 指标名 |
| `metadata.product_type` | **必须存在（路由关键）**   |
| `timestamp`             | 事件时间（非 DB 生成）    |

## 3. Ingress 层设计（协议接入）

Ingress 的职责只有一句话：

> **协议 → Raw Event**

### 3.1 Raw Event 统一结构

```json
{
  "payload": {
    "raw": "base64(...)",
    "topic": "...",     // MQTT / Sparkplug
    "path": "..."       // HTTP
  },
  "metadata": {
    "protocol": "http|mqtt|sparkplugb",
    "...": "协议特定字段"
  }
}
```

---

### 3.2 HTTP Ingress → Raw Event

#### 输入示例

```http
POST /ingress/http/dbm
{
  "device_id": "dbm102",
  "data": {
    "alarm": false,
    "s20": 1103
  }
```

## 八、插件内部结构（Go 骨架）

```go
type AutoSchemaProcessor struct {
    db        *sql.DB
    cache     *SchemaCache
    policy    SchemaPolicy
}

func (p *AutoSchemaProcessor) Process(ctx sdk.RuntimeContext, e sdk.Event) error {
    table := resolveTable(e)
    fields := extractFields(e)

    schema := p.cache.GetOrLoad(table)
    diff := DiffSchema(schema, fields)

    if diff.NeedCreate {
        p.createTable(table)
    }

    for _, col := range diff.AddColumns {
        p.addColumn(table, col)
    }

    for _, change := range diff.TypeChanges {
        p.applyTypeChange(table, change)
    }

    return nil
}
```

# 数据处理流程 - Ingress 架构与 Source 配置

## 📋 概述

本文档描述规则引擎的 Ingress 架构、Ingress 与 Source Plugin 的连接方式，以及各 Source 节点的配置项说明。

**核心原则**：
- Ingress 是唯一的协议接入边界，所有外部数据必须通过 Ingress 接入
- Ingress 只做协议转换，不处理业务逻辑
- Ingress 发布 **Raw Event** 到 `ingress.{protocol}.raw`，由 Source Plugin 负责过滤和处理
- Source Plugin 不直接监听端口或连接 Broker，只通过 NATS Event 接收数据

### 主要组件

#### 1. Ingress 主入口 (`internal/server/ingress/ingress.go`)

**职责**：
- 启动和管理所有协议适配器（HTTP、MQTT）
- 创建 Event Bridge
- 处理下行命令事件

**关键方法**：
- `Run(ctx, cfg)`: 启动 Ingress，初始化所有协议适配器

#### 2. Event Bridge (`internal/server/ingress/eventbridge/bridge.go`)

**职责**：
- 将协议数据转换为统一的 Event 格式
- 发布 Raw Event 到 NATS Topic: `ingress.{protocol}.raw`
- 订阅和处理下行命令事件

**关键方法**：
- `PublishRaw(protocol, event)`: 发布 Raw Event 到 `ingress.{protocol}.raw`
- `SubscribeCommandEvents(handler)`: 订阅命令事件（`ingress.command.>`）

#### 3. HTTP Ingress (`internal/server/ingress/http/http_ingress.go`)

**职责**：
- 接收 HTTP POST 请求
- 构建 Raw Event 并发布到 `ingress.http.raw`

**接入端点**：
- `POST /ingress/http` 或 `POST /ingress/http/*`
- 健康检查：`GET /health`

#### 4. MQTT Ingress (`internal/server/ingress/mqtt/mqtt_ingress.go`)

**职责**：
- 作为 MQTT Broker（基于 mochi-mqtt）
- 通过 Hook 机制捕获所有 MQTT 消息
- 识别 SparkplugB Topic（`spBv1.0/` 前缀）
- 构建 Raw Event 并发布到 `ingress.mqtt.raw` 或 `ingress.sparkplugb.raw`

**SparkplugB Topic 识别**：
- Topic 格式：`spBv1.0/{group}/{MSG}/{node}/{device?}`
- MSG 类型：`NBIRTH`, `DBIRTH`, `NDATA`, `DDATA`, `DCMD`, `NCMD`, `NDEATH`, `DDEATH`
- 自动提取 `hint.*` 元数据：
  - `hint.group`: Group ID
  - `hint.msg`: 消息类型
  - `hint.node`: Node ID
  - `hint.device`: Device ID（如果有）

#### 5. Dispatcher (`internal/core/dispatcher/dispatcher.go`)

**职责**：
- 订阅所有 `ingress.*.raw` Topic
- 将 Raw Event 分发给所有注册的 Source Plugin
- 通过 `PluginClient.SendEvent()` 统一分发

**分发逻辑**：
```go
// Dispatcher 订阅 ingress.*.raw
ingressSubject := "ingress.*.raw"

// 收到 Raw Event 后，分发给所有规则的 Source Plugin
for _, rule := range d.rules {
    for nodeID, pClient := range rule.Plugins {
        if pClient.Info().Type == sdk.PluginTypeSource {
            // 非阻塞分发（Source Plugin 自己决定是否处理）
            go func(nid string, cl client.PluginClient, evt sdk.Event) {
                if err := cl.SendEvent(evt); err != nil {
                    utils.Debug("Source plugin %s rejected raw event: %v", nid, err)
                }
            }(nodeID, pClient, event)
        }
    }
}
```

## 🔄 Ingress 与 Source 的连接方式

### 连接流程

```
1. 外部数据接入
   └── HTTP POST /ingress/http
       MQTT Publish to Broker
       SparkplugB Publish to Broker

2. Ingress 协议转换
   └── Event Bridge.PublishRaw(protocol, event)
       └── 发布到 NATS Topic: ingress.{protocol}.raw

3. Dispatcher 分发
   └── 订阅 ingress.*.raw
       └── 通过 PluginClient.SendEvent(event) 分发给所有 Source Plugin

4. Source Plugin 接收
   └── OnEvent(event) 接收 Raw Event
       └── 根据配置过滤和处理事件

5. Source Plugin 发布
   └── EngineRPC.Emit(event)
       └── 发布到 NATS Edge Topic: rule.edge.{ruleID}.{fromNodeID}.{toNodeID}
       └── Dispatcher 继续分发到下游节点
```

### 连接特点

1. **广播模式**：所有 Source Plugin 都能接收到 Raw Event，由 Source Plugin 自己决定是否处理
2. **非阻塞分发**：Dispatcher 使用 goroutine 异步分发，不会阻塞
3. **协议无关**：Source Plugin 只处理统一的 Event 格式，不关心协议细节
4. **过滤机制**：Source Plugin 根据配置（如 topic 匹配、group_id 匹配等）过滤事件

### Raw Event 结构

所有 Ingress 发布的事件都遵循统一的 Raw Event 格式：

```json
{
  "id": "uuid",
  "timestamp": "2024-01-01T00:00:00Z",
  "payload": {
    "raw": "base64_encoded_data",
    "topic": "mqtt/topic",  // MQTT/SparkplugB 特有
    "path": "/ingress/http"  // HTTP 特有
  },
  "metadata": {
    "protocol": "http|mqtt|sparkplugb",
    "method": "POST",          // HTTP 特有
    "client_id": "client-123", // MQTT 特有
    "qos": "0",                // MQTT 特有
    "hint.group": "Factory",   // SparkplugB 特有
    "hint.msg": "DDATA",       // SparkplugB 特有
    "hint.node": "Line1",      // SparkplugB 特有
    "hint.device": "Motor1"    // SparkplugB 特有
  }
}
```

## 📝 各 Source 节点配置项说明

### 1. HTTP Source (`source-http-ingress`)

**插件 ID**: `source-http-ingress`
**版本**: `1.5.0`
**协议**: `http`

#### 配置结构

```json
{
  "input": {
    "filter": {
      "expr": "string (可选)"
    }
  },
  "process": {
    "decode": {
      "body": "auto|json|text|binary"
    },
    "match": {
      "method": ["POST", "GET"],
      "path": "/ingress/http"
    }
  }
}
```

#### 配置项说明

| 配置项 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|--------|------|
| `input.filter.expr` | string | 否 | - | CEL 表达式，用于过滤事件（可选，当前版本暂未实现） |
| `process.decode.body` | string | 否 | `"auto"` | HTTP 请求体的解码方式：<br>- `auto`: 自动检测（尝试 JSON，失败则作为文本）<br>- `json`: 作为 JSON 解析<br>- `text`: 作为文本处理<br>- `binary`: 保持 base64 编码 |
| `process.match.method` | array[string] | 否 | - | HTTP 方法过滤，如 `["POST", "GET"]`。如果配置了，只处理匹配的方法 |
| `process.match.path` | string | 否 | - | 路径过滤，只处理匹配的路径 |

#### 处理逻辑

1. 检查 `metadata.protocol == "http"`
2. 根据 `process.match.method` 过滤（如果配置）
3. 根据 `process.match.path` 过滤（如果配置）
4. 解码 `payload.raw`（base64 解码后根据 `process.decode.body` 处理）
5. 设置 `RuleID` 和 `Source`
6. 发布事件到 DAG

## 🔑 关键设计原则

### 1. Ingress 是唯一协议接入边界

- ✅ 所有外部数据必须通过 Ingress 接入
- ❌ Source Plugin 不直接监听端口、不连接 Broker
- ✅ Source Plugin 只通过 NATS Event 接收数据

### 2. Raw Event 模式

- Ingress 只做协议转换，不处理业务逻辑
- Ingress 发布 Raw Event 到 `ingress.{protocol}.raw`
- Source Plugin 负责过滤和处理 Raw Event
- Source Plugin 根据配置（match、filter 等）过滤事件

### 3. 协议无关性

- Ingress 层处理协议细节（HTTP、MQTT、SparkplugB）
- Source Plugin 只处理 Event，不关心协议
- 通过 `metadata.protocol` 标识协议类型
- 通过 `hint.*` 元数据提供协议特定信息

### 4. 可扩展性

- 新增协议只需实现新的 Ingress 适配器
- Source Plugin 无需修改即可支持新协议
- 通过 `hint.*` 元数据支持协议特定功能

## 📌 注意事项

### 1. Source Plugin 过滤机制

- 所有 Source Plugin 都会收到 Raw Event
- Source Plugin 根据配置自行决定是否处理
- 如果过滤条件不匹配，Source Plugin 应该直接返回（不发布事件）

### 2. 性能考虑

- Raw Event 发布是异步的（非阻塞）
- Dispatcher 分发 Raw Event 也是异步的（goroutine）
- Source Plugin 应该快速处理 Raw Event，避免阻塞

### 3. Sparkplug Source 特殊处理

- Sparkplug Source 会为每个 metric 创建独立事件
- 这意味着一个 Sparkplug 消息可能产生多个 DAG 事件
- 下游节点需要考虑这种情况

### 4. Command Source 使用

- Command Source 用于下行命令，标记 `metadata.intent = "command"`
- 可以通过配置 `process.match.path` 区分不同的命令类型
- 通常与 Command Sink 配合使用，实现双向通信
