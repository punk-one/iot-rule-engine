- 审计日期：2026-09-04
- 审计基线：`2dd7b0f`
- 范围：启动与关闭、Manager/Executor/Pipeline、插件加载、认证、NATS/JetStream、存储、测试与仓库治理
- 限制：未进行公网渗透测试、真实集群故障注入、长稳压测和外部漏洞数据库查询

## 1. 结论

引擎已经形成 Ingress、Manager、Executor、Pipeline 四个运行面，并有插件进程隔离、规则运行时、Connector 资源总线、JetStream、DLQ、状态后端与较丰富的单元/集成测试。三仓拆分也改善了职责边界。

但当前基线存在必须先处理的安全与可靠性阻断项：仓库提交了可用形态的 NATS 用户凭证及私钥种子；固定默认管理员密码与缺少 RBAC 扩大了控制面风险；上传插件会在签名/信任验证前直接执行任意二进制。顶层服务错误不向主进程传播，关闭不等待子系统完成，也可能导致服务“进程存活但部分运行面已退出”。

| 维度 | 评级 | 判断 |
| --- | --- | --- |
| 可靠性 | C | 核心包测试通过，但服务监督、关闭顺序、部分发布错误处理不足 |
| 稳定性 | C | 全量普通测试通过；关键运行面 0% 覆盖，race 套件被时序测试阻断 |
| 可扩展性 | B- | 分层与接口较好；全局 bus、具体 Run 函数和硬编码基础设施限制多实例与替换能力 |

## 3. 分级发现

### ENG-001（P0）版本库包含 NATS 私钥种子

证据：以下 4 个已跟踪文件均包含 NATS User JWT 和 User NKey Seed 标记，且部署目录有重复副本：

- `configs/nats-sun2.creds`
- `configs/nats-sun-back.creds`
- `deploy/backend/configs/nats-sun2.creds`
- `deploy/backend/configs/nats-sun-back.creds`

影响：拥有仓库读取权限的人可使用种子派生签名并访问授权的 NATS 账户；仅从当前提交删除不能消除 Git 历史泄露。

整改状态（2026-09-04）：当前工作树已删除上述 4 个凭证文件及默认配置、打包脚本中的引用，并改为默认启动无凭证的内置 NATS。Git 历史清理、原凭证吊销/轮换仍需在发布前完成。

建议：立即在 NATS 侧吊销/轮换对应用户；确认审计日志；从当前树及历史中清除凭证；仓库只保留 `.example`；部署由 secret manager、受限文件挂载或 CI secret 注入。轮换必须先于公开推送。

### ENG-002（P0）插件上传等价于远程代码执行，当前无签名或沙箱

证据：

- `UploadPluginHandler` 保存上传文件并赋予执行权限。
- `VerifyPlugin` 会通过 `exec.Command(pluginPath)` 启动该文件，再读取其自报的 `PluginInfo`。
- checksum 只被计算和展示，没有与受信 manifest/签名比较。
- whitelist 在插件已经执行后才按其自报 ID 判断。

影响：任何能调用插件上传接口的主体都能以引擎操作系统用户权限执行任意程序。go-plugin 只提供进程隔离，不是权限沙箱。

建议：上传前验证受信发布者签名、artifact digest、大小、平台和 manifest；在独立低权限账户/容器/namespace 中验证与运行，限制文件、网络、系统调用和资源；控制面必须有 RBAC 和审计日志；生产可选择完全禁用在线上传。

### ENG-003（P0）固定默认管理员密码且没有角色授权

证据：`internal/server/manager/userauth/service.go` 内置固定默认管理员口令，并在空数据库启动时自动创建；用户模型没有角色/权限字段，Manager 路由除少数公开端点外只判断“已登录”，任何有效用户均可访问用户管理、插件上传、配置和规则接口。

影响：未首次改密的部署存在已知凭证；普通运维用户与管理员权限等同，可结合 ENG-002 获得主机代码执行能力。

建议：首次启动要求通过环境 secret/一次性 token 设置管理员密码，或生成随机密码并强制改密；增加 RBAC，至少区分只读、规则运营、插件发布、系统管理员；敏感操作写不可抵赖审计日志并支持会话撤销。

### ENG-004（P1）顶层没有监督子服务，启动失败会被静默降级

证据：`internal/server/engine.go` 用三个 goroutine 启动 Manager、Executor、Pipeline，这些 Run 函数不返回错误；监听端口失败、数据库 watch 失败、订阅失败等仅写日志后 goroutine 退出，`Engine.Run()` 已经返回成功，主进程继续等待信号。

影响：进程和基础 health 可能存活，但某个关键运行面永久不可用；外部进程管理器不会重启。

建议：统一使用 error group/supervisor；所有运行面返回 error；任一必需服务启动失败应让整体启动失败或进入明确 degraded 状态；readiness 必须验证 Manager、Executor、Pipeline、NATS、DB 与插件运行时。

### ENG-005（P1）关闭顺序没有等待运行面退出

证据：主函数在 context 取消后立即从 `Run` 等待返回并执行 `Engine.Close()`；`Engine.Close()` 先关闭全局 bus，再关闭共享 DB，没有 WaitGroup 等待 Manager、Executor、Pipeline goroutine 完成各自 Shutdown、watch cancel 和 flush。

影响：停止时可能在运行面仍使用 NATS/DB 时关闭底层资源，造成消息未 Ack、状态未落盘、日志噪声或竞态；systemd 停止窗口内无法确认排空完成。

建议：明确停止顺序：停止接入 → 停止拉取新任务 → 等待在途任务/插件 → flush/Ack/状态持久化 → 停止 watch → 关闭 HTTP → Drain NATS → 关闭 DB；每步有 deadline 和结果汇总。

### ENG-006（P1）升级插件不是原子操作，也没有可信回滚

证据：Upgrade 先卸载旧插件，再直接把上传文件写入目标路径并加载；失败时删除新文件，但旧进程与旧 artifact 未恢复。Upload 使用客户端文件名作为最终名称，可能覆盖已有文件；文件落盘和注册也没有事务。

影响：失败升级会导致插件不可用；并发上传或重名 artifact 可能覆盖；规则运行实例与管理目录状态可能分叉。

建议：上传到内容寻址的隔离目录，完整验证和健康探测后原子切换版本指针；保留旧版本与运行实例，切换失败自动回滚；并发操作用插件 ID 锁和状态机管理。

### ENG-007（P1）部分事件扇出失败会返回成功

证据：`Dispatcher.PublishEventToNodes` 对每个下游发布失败只记录日志并继续，循环结束后始终返回 `nil`。

影响：上游认为事件已完整发布并可能 Ack，但某些分支实际丢失；DAG 多分支场景出现不可见的部分成功。

建议：定义扇出原子性和部分失败模型；至少聚合失败目标并返回结构化错误，交由重试/DLQ/幂等处理；记录每个 edge 的交付状态。

### ENG-008（P1）HTTP 服务缺少防慢连接超时，pprof 可绕过鉴权

证据：Manager `http.Server` 只配置 Addr/Handler，没有 ReadHeaderTimeout、ReadTimeout、WriteTimeout、IdleTimeout 和 MaxHeaderBytes；启用 pprof 时挂在鉴权中间件之前；CORS 允许任意 Origin。

影响：慢连接可长期占用资源；pprof 可能泄露运行信息并触发高开销 profile；宽松 CORS 增加浏览器侧攻击面。

建议：配置合理 HTTP 超时与请求体上限；pprof 只监听 loopback/管理网或单独强认证；按部署域名限制 CORS。登录和上传增加速率限制。

### ENG-009（P1）生产路径遗留个人绝对路径调试埋点

证据：`internal/core/plugin/loader.go`、`internal/server/executor/executor.go`、`internal/core/engine/dag_nats.go` 多处将包含规则/节点/调试数据的 JSON 追加到 `/home/sun/workspace/iot-rule-engine/.cursor/debug.log`，错误被忽略。

影响：生产环境行为不一致；目标目录存在时会产生未轮转文件与潜在数据泄露，不存在时又静默失败；增加关键路径 I/O。

建议：发布前删除临时埋点，统一走结构化 logger，并经过级别、脱敏、采样和轮转配置。

### ENG-010（P2）关键运行面测试覆盖不足

证据：总体覆盖率 33.3%；`internal/server`、Executor、Manager 路由、Pipeline、Trace Hub 和 cmd 直接覆盖率为 0%。部分官方插件集成测试在源码不可用时会 Skip。

影响：服务组合、端口失败、启动回滚、停止排空、认证路由和运行面故障无法由当前流水线证明。

建议：增加进程级 smoke test、启动失败注入、优雅关闭、NATS 断开恢复、DB 故障、插件崩溃/升级回滚；修复 Scheduler 时序测试后让 race 成为强制门禁。

### ENG-011（P2）UI gitlink 和文档目录使新克隆不完整

证据：`ui` 是 gitlink（mode 160000），但没有 `.gitmodules`；README 引用 `docs/*.md`，实际主要文档位于 `docs/`，`docs/` 仅有 JSON fixture。

影响：新 clone 无法自动获得 UI；README 文档链接失效；部署构建不可复现。

建议：明确选择 submodule、独立仓库下载步骤或把 UI 正常纳入仓库；统一 `docs/` 并设置链接检查。本次审计遵守“不改代码”，仅在现有 `docs/` 添加报告。

### ENG-012（P2）依赖边界尚未随插件拆仓收敛

证据：引擎 `go.mod` 仍直接声明在引擎 Go 源码中无引用的 MQTT Paho、Redis v9、TDengine driver；插件仓有近似的完整依赖集合。

影响：增加依赖审计、许可证和漏洞响应范围，也容易让引擎受插件驱动升级影响。

建议：SDK 正式发布后运行 tidy 并审查差异；测试专用依赖单独说明；持续生成 SBOM。不要仅为减少行数盲目删除有构建标签用途的依赖。

### ENG-013（P2）会话与鉴权存在运维弱点

证据：会话只保存在进程内，重启全部失效；Bearer token 允许从 query 参数读取，URL 可能进入访问日志、代理和浏览器历史；密码只校验非空，没有强度或首次改密状态。

建议：禁止 query token；增加登录速率限制、密码策略、首次改密、全局撤销和审计；根据部署形态选择持久/共享会话或明确单实例限制。

### ENG-014（P0）分支任务共享 Event 可导致进程级 map 崩溃

证据：审计基线中的 `OnPluginEmit` 会直接修改插件传入的 Metadata，并以 `Event: *event` 向多个下游提交结构体浅拷贝；批量和 Pipeline 路径同样共享 Metadata 与嵌套 Payload。Observer、插件客户端或并行分支读写同一 map 时可触发 `fatal error: concurrent map read and map write`，该错误不能由 `recover` 捕获。

影响：任一高并发、多分支规则都可能导致整个引擎进程退出，而不只是单个规则或插件失败；共享来源字段也会造成边指标归属错误。

整改状态（2026-09-05）：已在插件发布边界和 Dispatcher 入口取得 Event 所有权；单事件、批量、Pipeline、DLQ 重放均为每个下游分支独立 Clone；FIFO Scheduler 入队再次克隆；发送给插件的事件与任务事件隔离；RuleID、FromNode、ToNode 和执行时间改为显式调度字段；Observer 只接收拥有独立 Payload 快照的值对象。新增并行分支、批量、Pipeline、Scheduler、插件反向修改和边指标测试，`go test -race ./...` 已通过。

剩余建议：将 Event 所有权规则加入架构契约和代码评审清单；性能压测应单独观察多分支深拷贝的 CPU 与分配，并据此设置 Payload 大小和扇出上限。

## 4. 正面能力

- `internal/core`、`infra`、`server` 分层清晰，RulesDB、StateBackend、Plugin/Connector 等存在接口边界。
- JetStream 使用手动 Ack、durable consumer、重连恢复和 DLQ/ACK/TRACE 独立 stream。
- Connector ResourceBus 包含配额、健康、warmup、provider 与 stream 测试。
- 配置解析、规则清洗、调度、中间件、运行态和存储均有一定测试基础。
- 插件使用独立进程，崩溃不会直接破坏引擎地址空间。
- 三仓拆分避免正式插件继续引用引擎内部包。

## 5. 可扩展性判断

适合继续扩展的边界：

- 新状态后端通过既有接口增加；
- 新 RulesDB 实现通过 factory 注册；
- 新 Dispatcher middleware、runtime observer 和 Connector provider 可沿现有结构扩展；
- 新插件应全部在独立插件仓实现，只依赖 SDK。

扩展前应先消除的耦合：

- 全局 `bus` 单例不利于测试、多实例和多租户；
- NATS stream 名称、保留期和存储类型硬编码；
- Run 函数只记录错误，不返回生命周期状态；
- 多处 `context.Background()` 切断调用方取消与 deadline；
- 插件信任、artifact 与运行实例没有独立领域模型。

## 6. 整改顺序

1. 立即轮换并清除 NATS 凭证，阻止公开推送。
2. 关闭或加固在线插件上传，完成签名、RBAC、沙箱和审计。
3. 移除固定默认密码，建立首次初始化流程。
4. 重构顶层 supervisor 与优雅关闭顺序。
5. 修复插件升级事务、扇出部分失败和 HTTP 安全边界。
6. 删除调试埋点，恢复 race 门禁并补运行面测试。
7. 收敛 UI、docs、依赖和发布治理。

## 7. 单插件进程多规则实例整改（2026-09-05）

原实例运行器会对每个规则节点调用 `SpawnPlugin`，导致规则/节点数量直接放大插件 OS
进程数。现已改为 Loader 进程池：canonical artifact 路径相同的普通插件只保留一个
HashiCorp go-plugin Client，规则节点通过 `plugin_factory` 获取独立 RPC/Plugin 对象。

为避免进程共享导致状态串线，本轮同时完成：

- SDK factory 每次 Dispense 创建新对象；
- 每个实例使用唯一反向 RPC BrokerID；
- 活动实例计数阻止进程卸载、替换和重载；
- Stop 只释放规则实例，重复释放幂等；
- `latest` 软链和版本化路径解析到同一 artifact 时复用同一进程；
- Connector Host 不再按 ProviderPolicy 扩展进程，多个资源共享一个 Connector 进程；
- 增加真实插件二进制集成测试，验证两个实例共享 Client/进程但不共享 RPC 对象。

该模型把故障域从“单规则实例进程”提升为“单插件 artifact 进程”。因此插件进程崩溃
会影响所有引用该 artifact 的规则；恢复时必须由规则恢复流程重新创建全部实例，不能
只恢复某一个旧 RPC 连接。
