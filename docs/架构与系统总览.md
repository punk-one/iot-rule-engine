## 🎯 第一阶段：基础概念和架构概览

### 学习目标

- 理解系统的定位和核心价值

- 了解整体架构设计

### 1.1 系统定位

**IoT Rule Engine** 是一个以 DAG 为核心、以插件为边界、以可视化为入口的云边规则执行平台。

#### 核心价值

1. **可视化编排**：通过 Canvas 拖拽方式设计规则，所见即所得
2. **插件化扩展**：通过插件扩展能力，无需修改引擎核心代码
3. **进程级隔离**：每个插件运行在独立进程中，互不干扰
4. **统一数据通道**：所有数据流经 NATS，显式优于隐式
5. **完整可观测性**：基于 Runtime Model 的实时监控和追踪

#### 适用场景

- **IoT 数据处理**：设备数据采集、过滤、转换、存储
- **实时流处理**：事件流处理、窗口聚合、变化检测
- **规则引擎**：业务规则编排、条件判断、路由分发
- **数据管道**：ETL 流程、数据清洗、格式转换

### 1.2 核心概念

#### DAG（有向无环图）

DAG 是系统的核心抽象，表示规则的执行拓扑。

```
Source → Processor → Sink
   ↓         ↓
Processor → Sink
```

**关键特性**：
- 节点（Node）：代表一个插件实例
- 边（Edge）：代表数据流向
- 无环：不允许循环依赖
- 显式：图上画出的连线 = 实际执行路径

#### Plugin（插件）

所有节点都是 Plugin，统一使用同一套接口。

**插件类型**：
- **Source Plugin**：产生事件（如 HTTP Source、MQTT Source）
- **Processor Plugin**：处理事件（如 Filter、Map、Window）
- **Sink Plugin**：消费事件（如 Mock Sink、Postgres Sink）

**统一接口**：
```go
type Plugin interface {
    Info() PluginInfo
    Init(cfg PluginConfig) error
    Start(ctx RuntimeContext) error
    OnEvent(e Event) error  // 接收事件
    Stop() error
}
```

#### Event（事件）

Event 是系统中数据流转的基本单位。

```go
type Event struct {
    ID        string                 // 事件唯一ID
    Timestamp time.Time              // 时间戳
    RuleID    string                 // 规则ID
    Source    string                 // 来源节点ID
    Payload   map[string]interface{} // 业务数据
    Metadata  map[string]string      // 元数据（trace_id、rule_id等）
}
```

#### Dispatcher（调度器）

Dispatcher 是系统的核心中枢，负责：
- 订阅 NATS Edge Topic
- 解析事件并分发到目标插件
- 管理插件运行时
- 通过 Hooks 更新 Runtime Model

**唯一职责**：把 Event 从一个 Node，可靠地送到下一个 Node

### 1.3 整体架构

#### 三层架构

```
┌─────────────────────────────────────┐
│         UI / API 层                  │
│  (规则管理、可视化编辑、运行态监控)    │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│         Engine 层                     │
│  ┌──────────┐  ┌──────────────┐    │
│  │ RuleMgr  │  │ Dispatcher   │    │
│  └──────────┘  └──────────────┘    │
│  ┌──────────┐  ┌──────────────┐    │
│  │PluginMgr │  │ EngineRPC    │    │
│  └──────────┘  └──────────────┘    │
└──────────────┬──────────────────────┘
               │ RPC (go-plugin)
┌──────────────▼──────────────────────┐
│      External Plugins 层             │
│  Source | Processor | Sink           │
└──────────────────────────────────────┘
```

#### 核心组件

| 组件 | 职责 | 位置 |
|------|------|------|
| **Engine** | 顶层引擎，管理所有服务生命周期 | `internal/server/engine.go` |
| **Rule Manager** | 规则管理，提供 REST API | `internal/server/manager/` |
| **Plugin Manager** | 插件生命周期管理 | `internal/plugin/loader.go` |
| **Dispatcher** | 事件调度和路由 | `internal/dispatcher/dispatcher.go` |
| **Ingress** | 协议接入层 | `internal/ingress/` |
| **Runtime Manager** | 运行态模型管理 | `internal/runtime/manager.go` |
| **Runtime Observer** | 运行态观测器 | `internal/runtime/observer.go` |

### 1.4 核心设计原则

1. **统一 Plugin 模型**：所有节点都是 Plugin，使用同一套接口
2. **统一数据通道**：所有数据流经 DAG（基于 NATS），显式优于隐式
3. **显式优于隐式**：图上画出的连线 = 实际执行路径
4. **结构稳定，能力扩展**：通过插件扩展能力，而不是引擎分支逻辑
5. **进程级隔离**：插件通过 go-plugin 实现进程隔离

### 2.1 数据面信息流

数据面负责事件在系统中的流转，从 Ingress 接入到最终输出。

#### 上行数据流（Telemetry）

```
外部系统/设备
    ↓
Ingress (协议接入层)
    ├── HTTP: POST /ingress/http/{source_id}
    ├── MQTT: Hook Adapter 捕获消息
    └── Sparkplug: Topic 解析
    ↓
Event Bridge
    └── PublishRaw() → NATS: ingress.{protocol}.raw
    ↓
Dispatcher
    ├── 订阅 ingress.*.raw
    ├── onIngressRaw() 处理 Raw Event
    └── 分发给所有 Source Plugin
         ├── OnIngressEvent Hook → RuntimeObserver（更新 Source EventsIn）
         └── PluginRPC.ReceiveEvent() → Plugin.OnEvent()
    ↓
Source Plugin
    ├── OnEvent() 接收 Raw Event
    ├── 根据 hint 字段过滤
    └── EngineRPC.Emit() → Dispatcher.OnPluginEmit()
         ├── OnNodeEmit Hook → RuntimeObserver（更新 Source EventsOut）
         ├── Router.Resolve() / RuleRuntime.Edges
         └── Scheduler.Submit() → NATS Edge Topic
    ↓
NATS Edge Topic: rule.edge.{ruleID}.{fromNodeID}.{toNodeID}
    ↓
Dispatcher.onMessage()
    ├── 订阅所有 Edge Topic (rule.edge.{ruleID}.>)
    ├── 解析事件，提取 toNodeID
    └── Scheduler.executeTask()
         ├── OnNodeReceive Hook → RuntimeObserver（更新 Processor/Sink EventsIn）
         ├── PluginClient.SendEvent() → PluginRPC.ReceiveEvent()
         └── OnTaskDone Hook → RuntimeObserver（更新错误计数，如有错误）
    ↓
Processor Plugin
    ├── OnEvent() 接收事件
    ├── 处理事件（过滤/转换/聚合等）
    └── EngineRPC.Emit() → Dispatcher.OnPluginEmit()
         ├── OnNodeEmit Hook → RuntimeObserver（更新 Processor EventsOut）
         └── 继续流转到下游节点
    ↓
Sink Plugin
    ├── OnEvent() 接收事件
    └── 输出到外部系统（数据库/消息队列/API等）
         └── OnTaskDone Hook → RuntimeObserver（更新 Sink 执行状态）
```

#### 关键数据流节点

**1. Ingress → Event Bridge**

```go
// HTTP Ingress 示例
func (h *HTTPIngress) handleIngress(w http.ResponseWriter, r *http.Request) {
    // 1. 解析 source_id
    sourceID := extractSourceID(r.URL.Path)

    // 2. 构建 Raw Event
    event := sdk.Event{
        ID:        uuid.New().String(),
        Timestamp: time.Now(),
        Payload:   parseBody(r.Body),
        Metadata:  map[string]string{
            "protocol": "http",
            "source_id": sourceID,
        },
    }

    // 3. 发布到 NATS
    bridge.PublishRaw("http", sourceID, event)
}
```

**2. Dispatcher → Source Plugin**

```go
// Dispatcher 分发 Raw Event 给 Source Plugin
func (d *Dispatcher) onIngressRaw(data []byte) error {
    // 1. 解码 Raw Event
    var event sdk.Event
    json.Unmarshal(data, &event)

    // 2. 分发给所有 Source Plugin
    for _, rule := range d.rules {
        for nodeID, pClient := range rule.Plugins {
            if pClient.Info().Type == sdk.PluginTypeSource {
                // 3. 发送事件
                pClient.SendEvent(event)

                // 4. 更新 Metrics
                if d.hooks.OnIngressEvent != nil {
                    d.hooks.OnIngressEvent(ruleID, nodeID, &event)
                }
            }
        }
    }
}
```

**3. Plugin → Dispatcher**

```go
// Plugin 通过 EngineRPC.Emit() 发布事件
func (p *MyPlugin) OnEvent(e sdk.Event) error {
    // 处理事件
    processed := process(e)

    // 发布到下游
    return p.ctx.EngineRPC().Emit(processed)
}

// EngineRPC.Emit() 实现
func (s *EngineRPCServer) Emit(e sdk.Event) error {
    // 调用 Dispatcher.OnPluginEmit()
    return s.dispatcher.OnPluginEmit(s.ruleID, s.nodeID, &e)
}
```

**4. Dispatcher → Processor/Sink Plugin**

```go
// Dispatcher 分发事件到下游插件
func (d *Dispatcher) executeTask(task *DispatchTask) error {
    // 1. 更新 Metrics（接收事件）
    if d.hooks.OnNodeReceive != nil {
        d.hooks.OnNodeReceive(task.RuleID, task.ToNode, &task.Event)
    }

    // 2. 发送事件到插件
    err := client.SendEvent(task.Event)

    // 3. 更新 Metrics（任务完成）
    if d.hooks.OnTaskDone != nil {
        d.hooks.OnTaskDone(task.RuleID, task.ToNode, &task.Event, err)
    }

    return err
}
```

### 2.2 控制面信息流

控制面负责规则和插件的生命周期管理，以及运行态观测。

#### 规则启动流程

```
1. Engine 创建 DAG Executor
   ├── 创建 RuntimeManager 实例
   ├── 创建 RuleInstance（Runtime Model）
   ├── 创建 Dispatcher（ruleID）
   ├── 创建 RuntimeObserver 并注入到 Dispatcher Hooks（v1.4.0）
   └── 初始化 State Manager（如需要）

2. Engine 加载插件（plugin.Loader）
   ├── 扫描插件目录
   ├── 启动插件进程（go-plugin）
   ├── 建立 RPC 连接（PluginRPCClient）
   └── 调用 PluginRPC.Info() 获取插件信息

3. Engine 为每个插件创建 RuntimeContext
   ├── 在 Engine 端创建 EngineRPCServer（注入 Dispatcher）
   ├── 创建 PluginContext（包含 EngineRPCServer）
   └── 调用 PluginRPC.Start()，传入 RuntimeContext

4. Plugin Loader 启动插件
   ├── 从 RuntimeContext 获取 EngineRPCServer（Engine 端创建）
   ├── 注册 Engine RPC 服务（ID: 3，v1.4.0 仅保留 Engine RPC）
   └── 调用 PluginRPC.Start()，插件保存 PluginRPCClient

5. Engine 注册插件到 Dispatcher
   ├── 创建 PluginClient（ExternalPluginClient，所有插件都是外部插件）
   ├── 创建 NodeInstance（Runtime Model）
   ├── 插件加载失败时返回错误（Rule 级 Fail-Fast）
   └── Dispatcher.RegisterPluginToRule(nodeID, pluginClient)

6. Engine 启动 Dispatcher
   ├── Dispatcher.Start()
   ├── 订阅 NATS Edge Topic: rule.edge.{ruleID}.>
   ├── 订阅 Ingress Raw Topic: ingress.*.raw
   └── 等待事件到达

7. Source Plugin 开始工作
   ├── 通过 OnEvent 接收 Raw Event（由 Dispatcher 分发）
   ├── OnIngressEvent Hook → RuntimeObserver（更新 EventsIn）
   ├── 根据 hint 字段过滤事件
   └── EngineRPC.Emit() → Dispatcher.OnPluginEmit() → NATS Edge Topic
         └── OnNodeEmit Hook → RuntimeObserver（更新 EventsOut）
```

#### 事件处理流程

```
1. Source Plugin 发布事件
   Source Plugin → EngineRPC.Emit() → Dispatcher.OnPluginEmit()
   ├── OnNodeEmit Hook → RuntimeObserver（更新 EventsOut）
   ├── Router.Resolve() / RuleRuntime.Edges
   └── Scheduler.Submit() → NATS Edge Topic

2. Dispatcher 接收事件
   NATS Edge Topic → Dispatcher.onMessage()
   ├── 解析 subject，提取 toNodeID
   ├── 解码事件
   └── Scheduler.executeTask()

3. Dispatcher 分发事件（executeTask）
   ├── OnNodeReceive Hook → RuntimeObserver（更新 EventsIn）
   ├── PluginClient.SendEvent() → PluginRPC.ReceiveEvent() (RPC)
   └── Plugin.OnEvent() (插件处理事件)

4. Plugin 处理事件
   Plugin.OnEvent() → 处理逻辑 → EngineRPC.Emit() (如需要)
   └── OnTaskDone Hook → RuntimeObserver（更新错误计数，如有错误）

5. 事件继续流转
   重复步骤 1-4，直到到达 Sink Plugin
```

#### 规则停止流程

```
1. Engine 停止 Dispatcher
   Dispatcher.Stop()
   ├── 取消所有 NATS 订阅
   └── 停止所有插件

2. Engine 停止所有插件
   PluginRPC.Stop() → Plugin.Stop()

3. Engine 清理资源
   ├── 关闭 RPC 连接
   ├── 终止插件进程
   └── 清理 State Manager
```

### 2.3 Runtime Model 运行态模型

Runtime Model 是运行态观测的核心，通过 RuntimeObserver 统一更新。

#### 核心数据结构

**RuleInstance（规则运行实例）**
```go
type RuleInstance struct {
    ID        string                   // runtime_rule_id
    RuleID    string                   // 配置态 rule_id
    Version   string                   // 规则版本
    Status    RuleStatus               // created, running, paused, failed, stopped
    CreatedAt time.Time
    StartedAt time.Time
    StoppedAt *time.Time
    Nodes     map[string]*NodeInstance // 节点运行实例
    Edges     map[string]*EdgeInstance // 边运行实例
    Metrics   RuleMetrics              // 规则聚合指标
}
```

**NodeInstance（节点运行实例）**
```go
type NodeInstance struct {
    ID          string      // runtime_node_id (格式: instanceID-nodeID)
    NodeID      string      // canvas node id
    PluginID    string
    Version     string
    Status      NodeStatus  // init, running, idle, error, stopped
    StartedAt   time.Time
    InputEdges  []string
    OutputEdges []string
    Metrics     NodeMetrics // 节点指标
    LastError   *NodeError  // 最近错误
}
```

**NodeMetrics（节点指标）**
```go
type NodeMetrics struct {
    EventsIn     int64      // 输入事件数
    EventsOut    int64      // 输出事件数
    EventsFailed int64      // 失败事件数
    AvgLatencyMs float64    // 平均延迟（毫秒）
    LastEventAt  *time.Time // 最后事件时间
}
```

**EdgeInstance（边运行实例）**
```go
type EdgeInstance struct {
    ID       string      // runtime_edge_id
    EdgeID   string     // canvas edge id
    FromNode string
    ToNode   string
    Topic    string     // NATS Topic
    Metrics  EdgeMetrics // 边指标
}
```

**TraceEvent（Trace 事件）**
```go
type TraceEvent struct {
    InstanceID string
    TraceID    string
    RuleID     string
    NodeID     string
    EventID    string
    Status     string      // success, failed, processing
    Message    string
    Payload    interface{}
    Timestamp  time.Time
}
```

#### RuntimeObserver 机制（v1.4.0）

**RuntimeObserver** 是 Runtime 唯一写入口，通过 Dispatcher Hooks 更新 Metrics 和 Trace。

**Dispatcher Hooks**：
```go
type DispatcherHooks struct {
    // OnIngressEvent 当 Source Plugin 收到 Raw Event 时调用
    OnIngressEvent func(ruleID, nodeID string, event *sdk.Event)

    // OnNodeReceive 当节点接收事件时调用（上游 → 当前节点）
    OnNodeReceive func(ruleID, nodeID string, event *sdk.Event)

    // OnNodeEmit 当节点发出事件时调用（当前节点 → 下游）
    OnNodeEmit func(ruleID, nodeID string, event *sdk.Event)

    // OnTaskDone 当任务执行完成时调用（Processor / Sink 执行完成）
    OnTaskDone func(ruleID, nodeID string, event *sdk.Event, err error)
}
```

**更新流程**：
```
Dispatcher.executeTask()
     ├── OnNodeReceive Hook → RuntimeObserver.OnNodeReceive()
     │   └── IncrementNodeMetrics(eventsIn=1)
     ├── PluginClient.SendEvent()
     └── OnTaskDone Hook → RuntimeObserver.OnTaskDone()
         └── IncrementNodeMetrics(eventsFailed=1)（如有错误）
```

### 2.4 NATS Topic 规范

**Edge Topic**：
```
rule.edge.{ruleID}.{fromNodeID}.{toNodeID}
```

**Ingress Raw Topic**：
```
ingress.{protocol}.raw
```

**示例**：
- `rule.edge.rule-1.source-1.filter-1`：规则 rule-1 中从 source-1 到 filter-1 的边
- `ingress.http.raw`：HTTP Ingress 的原始事件
- `ingress.mqtt.raw`：MQTT Ingress 的原始事件

### 2.5 RPC 通信模型

#### EngineRPC（插件 → 引擎）

**接口定义**：
```go
type EngineRPC interface {
    Emit(e Event) error                    // 发布事件到下游节点
    EmitWithTargets(e Event, toNodeIDs []string) error  // 发布到指定节点
    Log(level LogLevel, msg string, fields map[string]interface{})  // 记录日志
}
```

**实现**：
- `EngineRPCServer`：引擎端 RPC 服务端（`internal/plugin/rpc/engine_rpc.go`）
- `EngineRPCClient`：插件端 RPC 客户端（`sdk/engine_rpc_client.go`）
- RPC ID: 3（v1.4.0 统一使用）

#### PluginRPC（引擎 → 插件）

**接口定义**：
```go
type PluginRPC interface {
    Info() PluginInfo                      // 插件元信息
    Init(cfg PluginConfig) error           // 初始化
    Start(ctx RuntimeContext) error         // 启动
    ReceiveEvent(e Event) error            // 接收事件（v1.4.0 核心）
    Stop() error                           // 停止
}
```

**实现**：
- `PluginRPCServer`：插件端 RPC 服务端（`sdk/rpc.go`）
- `PluginRPCClient`：引擎端 RPC 客户端（`sdk/rpc.go`）

#### 3.2.1 插件开发流程

**1. 创建插件项目**

**2. 实现 Plugin 接口**

```go
package main

import (
    "github.com/punk-one/iot-rule-engine/sdk"
)

type MyPlugin struct {
    config *Config
}

// Info 返回插件能力声明
func (p *MyPlugin) Info() sdk.PluginInfo {
    return sdk.PluginInfo{
        ID:          "my-plugin",
        Name:        "My Plugin",
        Version:     "1.0.0",
        Description: "My custom plugin",
        Type:        sdk.PluginTypeProcessor,
        Category:    "custom",
        Capabilities: sdk.PluginCapabilities{
            InputPorts:   1,
            OutputPorts:  1,
            SupportBatch: false,
            SupportAck:   false,
            ConfigSchema: `{
                "type": "object",
                "properties": {
                    "field": {"type": "string"}
                },
                "required": ["field"]
            }`,
        },
    }
}

// Init 初始化插件
func (p *MyPlugin) Init(cfg sdk.PluginConfig) error {
    // 解析配置
    var config Config
    if err := json.Unmarshal(cfg.Raw, &config); err != nil {
        return err
    }
    p.config = &config
    return nil
}

// Start 启动插件
func (p *MyPlugin) Start(ctx sdk.RuntimeContext) error {
    // 保存 RuntimeContext
    p.ctx = ctx
    return nil
}

// OnEvent 接收事件
func (p *MyPlugin) OnEvent(e sdk.Event) error {
    // 处理事件
    processed := p.process(e)

    // 发布到下游
    return p.ctx.Emitter().Publish(processed)
}

// Stop 停止插件
func (p *MyPlugin) Stop() error {
    return nil
}

// process 处理事件逻辑
func (p *MyPlugin) process(e sdk.Event) sdk.Event {
    // 业务逻辑处理
    return e
}

func main() {
    sdk.RunPlugin(&MyPlugin{})
}
```

# IoT Rule Engine 系统架构说明 (2026-01-09)

## 1. 系统项目拆解方案

为了提高系统的可维护性、扩展性以及生态建设能力，建议将当前项目拆分为三个独立的开源项目：

### 1.1 `iot-rule-engine` (核心引擎)
- **定位**：规则引擎运行态与可视化管理平台。
- **核心功能**：
    - DAG 编排与生命周期管理。
    - 基于 NATS 的统一事件总线。
    - 规则部署、运行态监控 (Runtime Model)。
    - 管理 UI (Canvas 编辑器、仪表盘)。
    - **现状**：当前主仓库的核心部分。

### 1.2 `punk-plugin-sdk` (插件开发 SDK)
- **定位**：标准化的插件集成接口与辅助工具。
- **核心功能**：
    - 定义 `Plugin`、`RuntimeContext`、`Event` 等核心接口。
    - 提供基于 HashiCorp `go-plugin` 的 RPC 桥接实现 (v1.5.0 Batch RPC)。
    - 提供日志缓存、指标自聚合等高性能基础设施。
    - **意义**：允许开发者在不克隆主引擎的情况下，独立开发并发布插件。

### 1.3 `punk-plugin-store` (插件商店/仓库)
- **定位**：插件的中心化分发与版本管理平台。
- **核心功能**：
    - 托管所有官方及社区贡献的插件源码或二进制产物。
    - 提供插件元数据查询（名称、描述、配置 Schema、兼容性）。
    - 插件热度、评分与分类管理。
    - **HUB 地址**：`https://hub.iot-rule-engine.com/`

---

## 2. 插件商店 (Hub) 架构与接口设计

### 2.1 商店架构
插件商店采用典型的 **Registry + Storage** 架构：
- **Web Portal**：开发者提交插件，用户浏览与搜索。
- **Registry API**：提供标准化的 RESTful 接口供引擎调用。
- **Metadata DB**：存储插件所有版本的元数据（含 `ConfigSchema`）。
- **Blob Storage**：存储插件的二进制程序包（针对不同 OS/Arch 的编译产物）。

### 2.2 核心 API 接口
引擎与商店的交互遵循以下接口规范：
- `GET /api/v1/plugins`: 查询插件列表（支持分类、关键词、SDK版本过滤）。
- `GET /api/v1/plugins/{id}`: 获取特定插件的详细信息及可用版本。
- `GET /api/v1/plugins/{id}/manifest?version={v}`: 获取指定版本的清单（含二进制下载地址、校验码）。
- `POST /api/v1/plugins/publish` (需鉴权): 开发者发布新插件/版本。

### 2.3 本地安装流程
1. **查询**：用户在本地 UI 的“插件管理”通过 `https://hub.iot-rule-engine.com/` 搜索应用。
2. **下载**：引擎根据当前系统架构（如 `linux/amd64`）请求下载对应二进制。
3. **校验与激活**：下载后进行 SHA256 校验，放入本地 `data/plugins` 目录，引擎热加载该插件。

---

## 3. 插件适配性与执行策略建议

针对“保证唯一适配性”还是“支持任意插件”的问题，参考业界成熟方案：

### 3.1 业界参考
- **Node-RED**：基于 NPM 生态。通过 `package.json` 中的 `engines` 字段管理 Node.js 与 Node-RED 版本兼容性。支持任意符合接口的包运行，生态极度开放。
- **n8n**：支持内置节点和社区节点 (Marketplace)。节点必须实现其特定的类接口。
- **1Panel**：基于 Docker 容器。所有应用（插件）都是容器化的，环境完全隔离，具有极强的通用性适配能力。

### 3.2 兼容性建议方案

**建议采用“SDK 版本契约制”的混合模式：**

1. **唯一适配性保证 (安全性/稳定性)**：
    - 每个插件必须在 `PluginInfo` 中声明其编译时使用的 `SDKVersion`。
    - 引擎在启动插件握手阶段，对比本地 SDK 版本。若主版本号不一致，则拒绝运行或标注为“不兼容”。
    - **私有生态**：对于企业内部定制插件，可以通过私钥签名，引擎只运行经过签名的“合规”插件。

2. **支持任意插件 (灵活性/生态)**：
    - 只要插件遵循 Punk RPC 协议（基于 `go-plugin`），即使不是通过商店安装的本地二进制，也应允许运行。
    - **开发者模式**：提供“允许运行未经验证插件”的开关，方便本地调试。

### 3.3 结论建议
- **初期**：优先保证 **SDK 版本的向后兼容性**。
- **商店规范**：商店应对上传的插件进行静态扫描（提取 ConfigSchema）和基础功能验证，确保带标记的“推荐插件”在当前引擎版本下 100% 可用。
- **用户视角**：对于来自商店的插件，系统应自动处理适配并在 UI 给出明确的兼容性提示；对于本地手动添加的插件，给予“风险提示”但允许运行。

| RPC    | gob 无法支持 map[string]interface{}       |
| 插件     | Plugin ID、路径、实例概念混乱                   |
| 规则生命周期 | Rule 与 RuleInstance 边界不清              |
| 可观测性   | Trace 逻辑分散，难以扩展                       |

---

### 1.2 v1.4 RC 的核心目标（非常重要）

> **v1.4 RC 不是加功能，而是“架构定型版本”**

**明确三条红线：**

1. ❌ 执行路径不允许直接操作 Runtime
2. ❌ Dispatcher 不允许感知 Metrics / Trace
3. ❌ Plugin / Engine 不允许共享状态

### Dispatcher 的核心逻辑（简化版）

#### Ingress Raw → Source

```go
func (d *Dispatcher) onIngressRaw(event *sdk.Event) {
    for _, rule := range d.rules {
        for _, src := range rule.SourcePlugins {
            if d.hooks.OnIngressEvent != nil {
                d.hooks.OnIngressEvent(rule.RuleID, src.NodeID, event)
            }
            go src.Client.SendEvent(*event)
        }
    }
}
```

---

#### Plugin Emit → 下游节点

```go
func (d *Dispatcher) OnPluginEmit(
    ruleID string,
    fromNodeID string,
    event *sdk.Event,
) {
    if d.hooks.OnNodeEmit != nil {
        d.hooks.OnNodeEmit(ruleID, fromNodeID, event)
    }

    toNodes := d.rules[ruleID].Next(fromNodeID)
    for _, to := range toNodes {
        if d.hooks.OnNodeReceive != nil {
            d.hooks.OnNodeReceive(ruleID, to.NodeID, event)
        }
        go to.Client.SendEvent(*event)
    }
}
```

# 规则引擎管理规范

## Rule Engine Governance Specification

### **Version v1.3.1（正式版）**

---

## 1. 文档目的与适用范围

本规范用于约束 **规则引擎 v1.3.1 版本** 中以下核心模块的**职责边界、生命周期、调用方式和数据流规范**：

* Engine（进程级控制器）
* Message Bus（NATS JetStream + KV）
* 规则存储（rules.db / BoltDB）
* Dispatcher / Scheduler
* Pipeline / Executor
* Plugin Runtime（全部外置插件）

目标：

> **消除隐式依赖、写死关键语义、保证规则引擎在单进程与分布式扩展下的可演进性**

---

## 2. 版本定位与设计原则

### 2.1 v1.3.1 的定位

| 项目        | 说明                       |
| --------- | ------------------------ |
| 目标        | 架构收敛与边界固化                |
| 是否引入新能力   | ❌ 不引入新业务能力               |
| 是否允许破坏性变更 | ⚠️ 允许内部 API 调整           |
| 核心关键词     | **职责隔离 / 生命周期唯一 / 语义写死** |

---

### 2.2 核心设计原则

1. **唯一事实源（Single Source of Truth）**

   * 规则配置只能来自 `rules.db`
2. **进程级基础设施唯一**

   * bus / storage 只能由 Engine 初始化
3. **消息通道具备业务语义**

   * 不允许“裸 subject”使用
4. **插件是外部系统**

   * 不感知 Engine 内部实现细节

---

## 3. Engine 生命周期规范（v1.3.1 强制）

### 3.1 Engine 的唯一职责

Engine 是 **唯一的进程级控制器**，负责：

* 初始化基础设施
* 组织模块生命周期
* 管理启动 / 关闭顺序

---

### 3.2 Engine 启动顺序（强制）

```text
1. Engine.Start()
2. ├─ bus.Init()              ← 只能在此调用
3. ├─ storage.Init(rules.db)
4. ├─ plugin.Loader.Init()
5. ├─ Dispatcher.Init()
6. ├─ Scheduler.Init()
7. ├─ Pipeline / Executor.Init()
8. └─ Engine.Run()
```

---

### 3.3 禁止行为（v1.3.1）

| 模块       | 禁止行为                |
| -------- | ------------------- |
| Executor | 调用 bus.Init / Close |
| Pipeline | 初始化 NATS / KV       |
| Plugin   | 创建 JetStream / KV   |
| Plugin   | 访问 rules.db         |
| 任意模块     | 多次 Init bus         |

---

## 4. Message Bus（internal/infra/bus）管理规范

### 4.1 bus 的角色定义

> **bus 是进程级消息基础设施，不是业务模块**

* 封装：

  * NATS 连接
  * JetStream Context
  * KV Runtime State
* 不承载业务逻辑

---

### 4.2 bus.Init / bus.Close 规范（v1.3.1 必须）

#### 4.2.1 初始化规则

* `bus.Init()`：

  * **只能调用一次**
  * **只能由 Engine 调用**
* 内部必须有 **Init Once 保护**

#### 4.2.2 关闭规则

* `bus.Close()`：

  * 由 Engine 在 Shutdown 阶段调用
  * 必须先 `Drain()` 再 `Close()`

---

### 4.3 Stream 语义与权限（v1.3.1 固化）

#### 4.3.1 核心 Stream 定义

| Stream      | 说明           |
| ----------- | ------------ |
| DATA_INGEST | 数据接入工作队列     |
| INGRESS     | Ingress 原始事件 |
| RULE_PIPE   | 规则入口事件       |
| RULE_EDGE   | DAG 边事件      |
| SYS_TRACE   | 系统追踪         |

---

#### 4.3.2 Producer / Consumer 语义（写死）

| Stream    | Producer   | Consumer          |
| --------- | ---------- | ----------------- |
| INGRESS   | Ingress    | Source Plugin     |
| RULE_PIPE | Dispatcher | Pipeline Executor |
| RULE_EDGE | Dispatcher | Node Executor     |
| SYS_TRACE | All        | Trace Service     |

> v1.3.1 不允许任何模块绕过该语义直接 Publish / Subscribe

---

### 4.4 禁止裸 subject 使用

#### ❌ 禁止

```go
bus.Publish("rule.edge.xxx", data)
```

#### ✅ 必须

```go
bus.PublishRuleEdge(ruleID, fromNode, toNode, data)
```

## 7. Dispatcher / Scheduler 规范

### 7.1 Dispatcher 的唯一职责

* 从 RULE_PIPE 接收规则输入

  * 计算 toNodeIDs
  * Emit RULE_EDGE 事件

### 7.2 Dispatcher 必须具备的信息

# 规则引擎技术规范文档（v1.1.1 - RC）

> 本版本在 v1.1.0-RC 基础上完成一次**命名与职责的最终收敛**：
> - 将 **Gateway** 明确重命名为 **Ingress**
> - 明确 Ingress / Rule Engine / Plugin 的"黄金切割线"
> - 彻底消除 Source Plugin 对协议监听的任何依赖
> - 固化"协议接入 ≠ 规则起点"的工程原则

---

## 1. 版本目标与设计原则

### 1.1 版本目标

- 形成 **单一、确定、可推理** 的规则执行模型
- 消除 Source Plugin 的"特殊路径"，避免隐式行为
- 强化 Canvas、引擎、插件三者的一致性
- 为插件生态和长期演进打下稳定基础

### 1.2 核心设计原则

1. **统一 Plugin 模型**：所有节点都是 Plugin
2. **统一数据通道**：所有数据流经 DAG（基于 NATS）
3. **显式优于隐式**：图上画出的连线 = 实际执行路径
4. **结构稳定，能力扩展**：通过插件扩展能力，而不是引擎分支逻辑

---

## 2. 系统总体架构说明

### 2.1 系统组件

- **Ingress（接入层）**
  - 提供所有对外协议接入能力
  - 不感知规则、不加载插件、不执行 DAG
  - 负责将外部请求统一转换为 Event

- **Rule Engine Core（计算层）**
  - 规则编排（DAG）
  - 插件生命周期管理（go-plugin）
  - 运行时调度与 Trace

- **NATS Bus（运行时总线）**
  - DAG 的唯一数据通道
  - 解耦 Source / Processor / Sink
  - 支持规则级与节点级扩展

- **Frontend Canvas**
  - 规则可视化建模
  - 插件配置与校验
  - Debug / DryRun

---

### 2.2 Ingress 内部结构

```
Ingress
 ├── Protocol Runtime
 │    ├── HTTP Ingress
 │    ├── MQTT Broker
 │    ├── Sparkplug Adapter
 │    └── gRPC Ingress
 │
 ├── Security
 │    ├── Auth / Token
 │    ├── TLS
 │    └── Rate Limit
 │
 └── Event Bridge
      └── Publish Event → NATS
```

> **Ingress 的唯一输出：Event（进入 NATS）**

---

### 2.3 数据流总览（统一模型）

```
┌────────────┐
│ Ingress    │  HTTP / MQTT / Sparkplug
└─────┬──────┘
      │ Event
┌─────▼──────┐
│ Source     │  Source Plugin（规则起点）
└─────┬──────┘
      │   (NATS Topic)
┌─────▼──────────────────────────┐
│        Rule DAG (Pipeline)      │
│  Filter / Map / Window / Script │
└─────┬──────────────────────────┘
      │
┌─────▼──────┐
│ Sink       │  Sink Plugin
└────────────┘
```

> **关键约束**：
> - Ingress ≠ Source Plugin
> - Ingress 负责"接入"，Source Plugin 负责"规则起点语义"
> - 即使在 Canvas 上 Source 直接连到 Sink
> - 运行时仍然：Source → NATS → Sink

---

## 3. Plugin 统一模型（v1.1.1）

### 3.1 Plugin 分类

| 分类 | 说明 | 是否产生数据 |
|----|----|----|
| Source Plugin | 数据入口 | 是 |
| Processor Plugin | 数据处理 | 否 |
| Script Plugin | 自定义逻辑 | 否 |
| Sink Plugin | 数据出口 | 否 |
| Utility Plugin | 编解码/辅助 | 否 |

> 分类标准：**是否作为 DAG 的起点节点**，而不是是否"输入/输出"。

---

### 3.2 Plugin 基础接口（统一）

```go
type Plugin interface {
    Info() PluginInfo
    Init(cfg PluginConfig) error
    Start(ctx Context) error
    Stop() error
}
```

- Source / Sink / Processor **完全一致**
- 不存在特殊接口、不存在直连能力

---

### 3.3 Plugin 能力描述（用于前端 & 校验）

```yaml
id: mqtt-source
type: source
category: messaging
version: 1.0.0
capabilities:
  input_ports: 0
  output_ports: 1
  config_schema: mqtt_source_schema.json
```

Canvas、后端、引擎 **共同依赖该声明**。

---

## 4. Source Plugin 规范（v1.1.1 收敛版）

### 4.1 Source Plugin 的唯一职责

Source Plugin 负责：

- **订阅 Ingress 或外部系统产生的 Event**
- 将 Event 作为 DAG 的起点发布
- 不监听端口、不注册路由、不感知协议实现

---

### 4.2 Source Plugin 支持的接入方式

| 模式 | 说明 |
|----|----|
| Ingress-Bound | 订阅 Ingress 发布的 Event |
| External | 自行连接外部 HTTP/MQTT/SDK 并产生 Event |

> 无论哪种模式，**出口只有一个：NATS**。

---

### 4.3 严格禁止的行为

- ❌ Source Plugin 启动 HTTP / MQTT Server
- ❌ Source Plugin 注册 Ingress 路由
- ❌ Source Plugin 直接调用 Sink Plugin
- ❌ Source Plugin 绕过 DAG 发布数据
- ❌ Source Plugin 内部维护"私有数据通路"

> 这些行为会导致：
> - 规则不可视
> - Trace 不完整
> - 调试与运维不可控
> - **被视为架构违规**

---

## 5. DAG 与 NATS 执行语义

### 5.1 DAG 是唯一执行模型

- 每一条 Canvas 连线 = 一个 NATS Topic
- DAG 节点 = Plugin 实例
- DAG 执行顺序 = Topic 拓扑

### 5.2 NATS 的角色

| 角色 | 说明 |
|----|----|
| 数据总线 | 解耦插件 |
| 执行顺序 | 保证 DAG 顺序 |
| 扩展点 | 支持多实例 Scale |

> NATS **不是可选组件**，而是规则引擎运行时的一部分。

---

## 6. Canvas 规则与校验（v1.1.1）

### 6.1 连线合法性规则

| 规则 | 说明 |
|----|----|
| Source 只能作为起点 | 入度 = 0 |
| Sink 只能作为终点 | 出度 = 0 |
| Processor 必须在中间 | 入度 ≥1 且 出度 ≥1 |
| 不允许孤立节点 | 必须连线 |

---

### 6.2 Source → Sink 的 Canvas 表现

- **允许**在图上直接连线
- **但不代表直连执行**

```text
Source ───► Sink
```

运行时等价于：

```text
Source → NATS Topic → Sink
```

- 插件注册中心统一管理
- 插件版本与规则强绑定

## 3. 数据流和控制流

### 3.1 数据流（事件流转）

```
外部系统/设备
    ↓
Ingress (internal/server/ingress/)
    ├── HTTP: POST /ingress/http → http/http_ingress.go
    ├── MQTT: Hook Adapter → mqtt/mqtt_ingress.go
    └── Sparkplug: Topic 解析 → mqtt/mqtt_ingress.go
    ↓
Event Bridge (eventbridge/bridge.go)
    └── PublishRaw() → NATS: ingress.{protocol}.raw
    ↓
Dispatcher (internal/core/dispatcher/)
    ├── 订阅 ingress.*.raw
    └── 分发给所有 Source Plugin（通过 PluginClient.SendEvent()）
    ↓
Source Plugin (pkg/plugins/sources/)
    ├── OnEvent() 接收 Raw Event
    ├── 根据 hint 字段过滤
    └── EngineRPC.Emit() → Dispatcher.OnPluginEmit()
    ↓
Dispatcher.OnPluginEmit()
    ├── Router.Resolve() / RuleRuntime.Edges
    └── Scheduler.Submit()
    ↓
NATS Edge Topic: rule.edge.{ruleID}.{fromNodeID}.{toNodeID}
    ↓
Dispatcher.onMessage()
    ├── 解析事件，提取 toNodeID
    └── PluginClient.SendEvent() → PluginRPC.ReceiveEvent()
    ↓
Processor Plugin (pkg/plugins/processors/)
    ├── OnEvent() 接收事件
    ├── 处理事件
    └── EngineRPC.Emit() → Dispatcher.OnPluginEmit()
    ↓
Dispatcher → PluginRPC.ReceiveEvent()
    ↓
Sink Plugin (pkg/plugins/sinks/)
    ├── OnEvent() 接收事件
    └── 输出到外部系统
```

### 3.2 控制流（规则生命周期）

```
1. Engine 创建 DAG Executor
   ├── 创建 Dispatcher（ruleID）
   └── 初始化 State Manager

2. Engine 加载插件（plugin.Loader）
   ├── 扫描插件目录
   ├── 启动插件进程（go-plugin）
   ├── 建立 RPC 连接
   └── 调用 PluginRPC.Info()

3. Engine 为每个插件创建 RuntimeContext
   ├── 在 Engine 端创建 EngineRPCServer（注入 Dispatcher）
   ├── 创建 PluginContext（包含 EngineRPCServer）
   └── 调用 PluginRPC.Start()

4. Plugin Loader 启动插件
   ├── 从 RuntimeContext 获取 EngineRPCServer
   ├── 注册 RPC 服务（Logger、Metrics、Engine）
   └── 调用 PluginRPC.Start()

5. Engine 注册插件到 Dispatcher
   ├── 创建 PluginClient（ExternalPluginClient）
   ├── 插件加载失败时返回错误（Rule 级 Fail-Fast）
   └── Dispatcher.RegisterPluginToRule()

6. Engine 启动 Dispatcher
   ├── Dispatcher.Start()
   ├── 订阅 NATS Edge Topic: rule.edge.{ruleID}.>
   └── 订阅 Ingress Raw Topic: ingress.*.raw

7. Source Plugin 开始工作
   ├── 通过 OnEvent 接收 Raw Event（由 Dispatcher 分发）
   ├── 根据 hint 字段过滤事件
   └── EngineRPC.Emit() → Dispatcher.OnPluginEmit()
```

## 4. 关键设计原则

### 4.1 v1.3.1 架构约束

1. **Engine 不执行业务逻辑**
   - Engine 只负责调度和管理
   - 不处理业务数据
   - 不维护插件状态
   - 不执行插件逻辑

2. **Plugin 不感知 DAG / NATS**
   - 插件不直接订阅 NATS
   - 插件不感知上下游节点
   - 插件不调用 ctx.Subscribe
   - 插件不操作 Dispatcher

3. **Dispatcher 是唯一数据路由者**
   - 所有事件路由都通过 Dispatcher
   - Dispatcher 统一订阅 Edge Topic
   - Dispatcher 统一分发事件到插件

4. **RPC 只用于控制与边界通信**
   - PluginRPC：Engine → Plugin（发送事件）
   - EngineRPC：Plugin → Engine（发布事件、记录日志）

5. **Event 是唯一数据载体**
   - 所有数据通过 Event 传递
   - Event 包含 Payload 和 Metadata

### 4.2 存储职责分离（v1.3.1）

- **rules.db (BoltDB)**：规则配置（唯一事实源）
  - 规则定义
  - 快照
  - 灰度发布配置
  - 生命周期状态

- **runtime_kv (NATS KV)**：运行时状态（非事实源，进程内/可丢）
  - 插件注册表
  - 临时状态
  - offset/watermark
