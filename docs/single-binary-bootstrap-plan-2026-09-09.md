# IoT Rule Engine 单文件启动与首次初始化方案

- 日期：2026-09-09
- 状态：设计方案，本轮不改变现有启动架构
- 目标：最终只分发一个规则引擎可执行文件；空数据目录可安全完成数据库、默认设置和管理员初始化

## 当前结论

当前系统仍依赖 `configs/config.yaml`，不能直接删除：`cmd/main.go` 默认把它传给配置加载器，
加载器会先读取 YAML，随后才打开 SQLite 并用数据库中的 `config.system` 覆盖。

删除 `rules.db` 后，现有代码会自动创建数据目录、SQLite 文件、规则/配置/Connector/快照/
用户等表，并把 YAML 写入新的 `config.system`。但首次创建管理员时必须提供合法的
`IOT_RULE_ADMIN_PASSWORD`；未提供时会明确失败，而不是使用仓库内固定口令。因此当前准确行为是：

```text
config.yaml 存在 + IOT_RULE_ADMIN_PASSWORD 合法
  -> 创建 rules.db 和表
  -> 写入默认系统配置
  -> 创建 admin
  -> 正常启动

config.yaml 缺失
  -> 配置加载阶段失败

rules.db 全新 + IOT_RULE_ADMIN_PASSWORD 缺失
  -> 管理员初始化失败，服务不启动
```

## 推荐目标架构

### 1. 可执行文件内置默认值和 Web UI

- 用 Go 类型定义版本化默认配置，默认 Manager 地址为 `:11011`，不再依赖完整 YAML；
- 用 `go:embed` 打包前端生产构建，Manager 同时提供 UI 静态资源和 `/api/v1`；
- 浏览器始终使用同源 `/api/v1`，修改 Manager 启动端口后无需再修改前端配置；
- 保留 `--config` 作为两个小版本的兼容迁移入口，最终仅用于显式导入，而非启动必需项。

### 2. 最小 bootstrap 不进入 SQLite

SQLite 无法保存“它自己在哪里”和“如何解密自己”。仅保留下列启动参数/环境变量：

| 启动项 | 默认值 | 用途 |
| --- | --- | --- |
| `--data-dir` / `IOT_RULE_DATA_DIR` | 平台约定的数据目录 | 定位 `rules.db`、日志和内置 NATS 数据 |
| `--listen` / `IOT_RULE_LISTEN` | `:11011` | Manager 与内嵌 UI 的统一监听地址 |
| `--master-key-file` | 无 | 可选，解密 SQLite 中的敏感设置 |
| `--plugin-cache-dir` | 数据目录下的版本化缓存 | 释放内嵌插件产物 |

其他运行设置以 SQLite 为权威来源。环境变量可做应急只读覆盖，但 UI 必须标记“被部署环境覆盖”。

### 3. 首次启动状态机

首次启动应持有进程级文件锁，并在单个数据库事务内执行：

1. 创建 SQLite 和 schema migration 表；
2. 按版本执行幂等 migration；
3. 写入内置默认系统设置和 `schema_version`；
4. 创建管理员；
5. 写入 `initialized_at` 和当前发行版本；
6. 提交事务后才启动 NATS、插件和规则运行面。

管理员初始化顺序建议为：

1. 生产/无人值守部署优先读取 password file 或 Secret 环境变量；
2. 交互终端可提示输入并要求确认；
3. 两者都没有时，生成一次性高强度随机密码，仅显示一次并强制首次登录修改。

不能把 `Admin@123456` 或其他固定默认密码编译进生产程序。开发模式可显式启用本机回环地址
专用的 dev profile，但必须在 UI 和日志中持续显示非生产警告。

### 4. 插件与“单文件”的边界

插件仍必须保持独立 OS 进程，不能静态链接进规则引擎进程，否则会破坏故障隔离和“一种插件
只启动一个进程、多个规则共享该插件进程”的既定生命周期。

若要求真正单文件分发，可把已签名的插件二进制压缩后嵌入引擎：首次启动释放到
`plugin-cache/<plugin-id>/<version>/<sha256>/`，校验签名与哈希后原子切换；运行时仍从该目录
启动独立插件进程。更易运维的备选方案是“单安装包”，内部包含引擎、UI 和插件，但安装后仍
保留清晰目录。

### 5. 故障与恢复原则

- 数据库不存在：执行首次初始化；数据库损坏：失败关闭并给出备份恢复提示，绝不静默重建；
- migration 失败：事务回滚，旧库保持可恢复；
- 多进程同时首次启动：只有持锁进程初始化，其他进程等待或明确退出；
- 默认配置、数据库 schema 和内嵌插件都带独立版本；升级前自动创建一致性备份；
- 管理员初始化口令不写日志、不写数据库明文、不返回给非本机请求。

## 分阶段落地

1. 增加内置默认配置与 bootstrap 参数，保持 YAML 兼容；
2. 增加初始化状态机、schema version、首次管理员引导和故障测试；
3. 将生产 UI 嵌入 Manager，统一同源访问；
4. 增加插件内嵌释放、签名校验和原子升级；
5. 一个版本周期内输出 YAML 弃用警告，再移除默认 YAML 依赖；
6. 发布单可执行文件与单安装包两种制品，完成 Linux 服务和容器验收。

## 验收标准

- 仅复制一个可执行文件到空目录即可启动，并创建完整数据目录和数据库；
- 首次管理员初始化安全、可自动化，且不存在固定生产密码；
- 修改 `--listen :12000` 后 UI 与 API 均由同一地址提供，无前端二次配置；
- 第二次启动不覆盖 SQLite 中的设置、用户、规则和 Connector；
- 删除数据库只触发明确的全新初始化，损坏数据库不会被误判为全新；
- 每种插件仍为独立进程，同一种插件无论多少规则只存在一个进程；
- 离线环境可完成 UI、插件释放和首次启动，不访问公网。
